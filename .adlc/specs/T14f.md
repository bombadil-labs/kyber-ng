# T14f — The Skills Seam: Procedural Memory

Status: OPEN (light ceremony — rumble for the design cells, one deterministic
build, no blind taste). Parent: T14e (`0eeb16e` on provisional/t14). Rails:
carried.

## The framing (the user's correction — binding vocabulary)

**A skill is NOT a delta. A skill is a derived entity — a view over its delta
stream.** Deltas are the events: each one SETS a property (or retracts) of a
named skill — signed, content-addressed, timestamped by its triggering delta,
append-only. The skill itself — name, description, body, version — exists ONLY
as the fold. `skill.read` returns the fold; the skill lens loads folds; nothing
stores "a skill" as a blob. This is the T14c architecture: the prompt isn't
stored, it's assembled; the canon isn't stored, it's resolved; a skill is a
view over its deltas, like everything else.

**The set-vs-merge distinction (a design cell, not a default):** the memory
canon MERGES (merge-is-union — facts accumulate; the atom). A skill property
is a VALUE, so its fold SUPERSEDES, not merges: the latest `skill_set` delta
wins whole-set across deltas (per-property phrasing is within-delta only —
H6); retractions negate. "Merge-is-union"
governs the fact layer; the skill view is last-set-wins. The rumble ratifies
this — it is a pin, not an assumption.

## The schema sketch (the rumble pins the cells)

- **The skill aggregate**: identified by NAME (the aggregate key — stable
  across updates; "greet-new-member" is the same skill through its versions).
  Properties: description, body, (metadata as the slice decides). Each property
  is SET by a `skill_set` delta (a new delta per property, or one delta setting
  the full current property set — a cell).
- **The fold**: `Skill.view(set, name)` — fold the name's deltas in order
  (by `{timestamp, id}` — D2): the latest `skill_set` FULL set wins
  whole-set (H6; per-property language applies only within one full-set
  delta); a retraction delta negates (the skill is :retracted/not-found);
  the store holds deltas, the view is derived on read. Deterministic (no
  wall-clock — deltas claim their triggering delta's timestamp).
- **Update lineage**: an update is a NEW `skill_set` delta (superseding). The
  stream is the history; the view is the current state; version is derived
  (a cell: count of set-deltas vs the latest delta's id).
- **Removal**: a retraction delta (retraction-is-negation — the atom). The
  stream retains everything; restoring a skill = retracting the retraction.
- **The gate**: `skill_policy` epochs — the T14c memory-gate family pattern:
  fail-closed when ungoverned (skill WRITES refuse), epoch-allowlisted writes,
  fork-aware (the `:none`/`:forked` arms precede decode — the T14d norm).
  Creating/updating/removing skills is a WRITE — governed by operator policy,
  not the agent's whim.
- **Use — two surfaces**: (a) `skill.read` — mirror of `memory.read`: gated,
  returns the FOLD; unknown/retracted skill → the not-found resolution (the
  B6 `unknown_entity` precedent); (b) the **skill lens** in prompt assembly —
  like the window lens: a deterministic salience match over the VIEWS'
  names/descriptions (never the raw streams), capped, so relevant procedures
  ride into context without bloating it.

## Open design cells (the rumble pins these)

D1 — skill_set delta shape: one delta per property vs one delta setting the
full property set (atomicity, lineage readability).
D2 — the fold's ordering authority: delta-order by what (timestamp? append
order? the store's sequence) — must be deterministic and fork-safe.
D3 — version derivation: count vs latest-delta-id vs explicit version property.
D4 — retraction granularity: whole-skill vs per-property retraction.
D5 — the skill_policy epoch schema: allowlist by skill name? by writer? the
memory-gate family mapping.
D6 — the lens: salience matching (exact-name? prefix? description-keyword?),
the cap (a number), and the fold-vs-stream input.
D7 — the gate's write surface: which deltas are gated (skill_set only? also
retractions? — a retraction is a write to the same aggregate).
D8 — the skill.read not-found resolution: mirror B6's `unknown_entity`
spelling or a skill-specific status.

## Acceptance criteria (shape)

AC1 — the fold: a skill's current view derives from its deltas (set,
supersede, retract) — deterministic, no wall-clock; the "skill is a view"
contract witnessed (a test that proves no blob exists — the view is empty
until deltas are folded).
AC2 — the gate: skill writes fail-closed ungoverned, epoch-governed otherwise,
fork-aware; the read side mirrors memory.read's gating.
AC3 — the lens: relevant skills ride into the prompt (capped, deterministic);
irrelevant ones don't.
AC4 — lineage: update + remove + restore round-trip; the stream is intact
throughout (auditability).
AC5 (live, if the slice grows a live surface) — otherwise the operational
gates stay as the regression net.

## Design resolution (converged plan)

The rumble (P1/P2/P3 → A1/A2/A3 → R1/R2/R3, `.adlc/rumble-t14f/`) converged
on every contested cell. The binding framing held throughout: **a skill is a
DERIVED ENTITY — a view over its delta stream — never a delta; skill
properties are VALUES, so the fold SUPERSEDES (latest set wins), unlike the
fact layer's merge-is-union.** The resolutions below are pins, not sketches.

### D1 — delta shape: FULL-SET `SkillSet` (easy)

One delta per write carrying the WHOLE property set: name, description, body,
plus an optional provenance pointer `source/{:delta, call, "triggered"}` —
the MemoryEntity precedent (genesis.ex:103-104). Partial per-property maps
are REJECTED: genesis has no map kind, and per-property folding tears views
no author wrote. Metadata: P2's optional JSON-string role is ADDED
(spec-licensed "metadata as the slice decides"). Supersede is WHOLE-SET (H6):
an ABSENT optional role is CLEARED — the newest full-set delta's omission of
`metadata` clears it, never leaves it sticky; per-property latest-wins
language (D2) applies only WITHIN a single full-set delta, never across
deltas.

### D2 — fold ordering: `{claims.timestamp, id}` (moderate)

The ONLY content-derived total order in the substrate is
`{claims.timestamp, id}` (memory.ex `resolve_set`; context_builder.ex:74;
tool_executor.ex:467) — and the only one a fold can read. "The store's
append sequence" does not exist at any resolution site: the fold input is a
`DeltaSet.t()` plain map (`%{id_hex => {claims, sig}}`), merge is
`Map.merge` (delta_set.ex:24), forward-admit == reverse-admit, iteration ≠
insertion — and an append-order fold would diverge between replicas under
merge-is-union. **The fold orders by `{timestamp, id}`** — total (ts ties
break on the content-derived id), fork-safe (content-derived, no sequence),
replica-identical. Supersede is whole-set across deltas (H6): the LATEST
full-set delta wins; per-property language applies only WITHIN one full-set
delta. A retraction negates. No wall-clock anywhere in the fold.

### D3 — version: count of ALL set-deltas (easy)

`version` is derived = the count of ALL the name's set-deltas —
retraction-immune: remove/restore keeps the version stable, and history is
never renumbered. (P3's live-only count rejected: it collapses on remove and
renumbers on restore.)

### D4 — retraction: delta-ID-targeted negation + RECURSIVE liveness (hard)

A retraction is a delta-ID-targeted negation of the head set-delta — never
positional name-targeting (policy.ex:177-182 negates delta-ids only; the
grammar has no name form). **SKILL-level liveness is pinned (H2)**: a skill
is not-found iff its ORDER-HEAD set-delta is retracted under
recursive-existential liveness; restore = negate every live negation of that
head. The fold answers the latest LIVE set under the head — removal of the
head NEVER exposes the prior version (that is the forbidden
"retraction-path rollback" in disguise); not-found resolves
`{"", "unknown_entity"}` (D8). A retraction of a NON-head set-delta is a
SILENT NO-OP (documented) — it never re-exposes an older set. Liveness is
RECURSIVE: a flat retracted-ids scan cannot express restore (retracting the
retraction), so the fold computes liveness through the negation chain. No
retraction-path rollback: rollback = a NEW superseding set (forward-only).
Absorbed legs:

- **N7**: multi-removal + restore witnesses — existential inertness (every
  unretracted removal must be negated before the skill lives again;
  double-remove/single-restore leg).
- **N3**: re-creation beats revival — a fresh `skill_set` after a retraction
  is a NEW lineage; the retraction stays in the stream for audit; re-created
  properties beat revived ones with no special case.

**The liveness oracle is the probe-2 truth table, pinned (H3)** — the fold's
liveness is GREENFIELD: recursive-existential through the WHOLE negation
chain, recomputed per read, never latched, iteration-order-independent. The
house negation pattern is FLAT in five places (policy.ex:177-182,
engine.ex:285-290, reactor.ex:426-430, reactor.ex:552-557,
attestation.ex:65-69) — a build by analogy copies it and breaks restore; do
NOT. The oracle (minted chains through the real door):

- B: set + remove → flat: retracted=true / recursive: live=false
- C: remove + restore (retract the retraction) → flat: retracted=true /
  recursive: LIVE=true — flat kills restore (AC4)
- D: DOUBLE-remove + SINGLE-restore → flat: retracted=true / recursive:
  live=FALSE — existential: must stay dead
- E: double-remove + double-restore → recursive: live=true
- F: restore then RE-REMOVE the restore → recursive: live=false

The epoch layer is deliberately FLAT (revocation permanent — probe 2b, L4) —
do NOT "unify" the two layers.

### D5 — the gate: REUSE the memory-family `allow_entity` context (easy)

`skill_policy` reuses `allow_entity` `{:entity, name, "writable"}` — ZERO
genesis change on the POLICY side (genesis.ex:84-87, policy.ex:141: the
allow_entity context already exists); the family "skill" disambiguates skill
entities from memory entities. This does NOT cover the SkillSet/skill-retract
@defs kinds — those are a SEPARATE genesis evolution (H5, see Deliverables). Epoch arms precede args
decode (the T14d norm):

- ungoverned → refuse `skill_policy: no governing epoch (fail closed)`
- forked → refuse `skill_policy: epoch forked (fail closed)`
- governed → allowlist check.

Write surface (N6): `skill.set` AND `skill.retract` are BOTH gated — a
retraction is a write to the same aggregate. `skill.read` is gated like
`memory.read`.

The governed→allowlist arm needs its OWN reason spelling (M5): the memory
family has three (policy.ex:33, 75-77), and `Policy.check_memory/2` returns
the *memory_policy* dialect (policy.ex:98-103) — so the skill layer gets its
own check function returning
`skill_policy: skill not allowed by the current epoch`. The skill_policy
layer is appended LAST in `policy_verdict/3` (L1 — tool_executor.ex:205-216;
the precedence chain is regression-frozen: appending is the only order that
provably cannot perturb the existing suite). One allowlist governs all three
surfaces (L3): `allow_entity` `{:entity, name, "writable"}` — the
"writable" context is stripped at epoch compile (policy.ex:147-151 keeps
only the entity id); no read/write allowlist split exists this slice.

### D6 — the lens: fail-closed born-here (hard)

The lens is a call-less content surface born this slice, so it is FAIL-CLOSED
from birth (N2 absorbed; the T14e url closure is the precedent — prompt.ex's
legacy epoch-blindness is not the norm): ungoverned AND forked ⇒ NO skills
ride; only epoch-filtered folds are eligible. NO GateDecision is emitted —
the lens is prompt assembly, not a gate.

- **Home**: the lens lives in `Prompt.assemble/4` (prompt.ex:44-70) — NOT
  ContextBuilder, which owns only the thin InferenceRequested delta and the
  conversation/window helpers (context_builder.ex:36-84).
- **Query scope**: PROMPT-RELATIVE (M3) — the request's own promptRef
  pointer, strictly below the prompt's timestamp (the T14c house norm,
  context_builder.ex `conversation_ref`); NEVER the conversation tail (a
  resumed request would match the wrong turn). Full-window scanning
  re-injects stale procedures (the negative leg's power).
- **Match**: exact-name tier (case-sensitive) FIRST, then `Assoc.digests`
  overlap ≥ 1 shared digest (assoc.ex:46-57 — CALLED, never re-implemented;
  one tokenizer discipline, no second dialect). The exact-name operation is
  SUBSTRING (`String.contains?/2` on the turn text — M2, implied by N1's
  own rationale). Two case dialects by pin (L2): exact-name is
  case-sensitive, the digest tier downcases (assoc.ex:52) — a mis-cased
  mention falls through to the digest tier, intended.
- **Rank (M1)**: `{-shared_digest_count, name}` — exact-name tier first,
  then shared-digest count DESC, ties on the content-derived name; total and
  deterministic. Ties are the norm (probe 5: unrelated sentences share ≥1
  digest), and the 4-skill cap selects among them.
- **Cap**: 4 skills AND 8192 note bytes, SKIP-AND-CONTINUE (M4) — a ranked
  skill that would blow the byte bound is omitted entirely, never truncated
  (selection, not repair), and SMALLER LATER skills may still fit
  (stop-at-first-overflow rejected). The 8192 counts the RENDERED note
  bytes — the `"Skill: <name>"` prefix + description + body, the exact bytes
  that ride into the prompt.
- **Note slot + format (M3)**: skill notes ride in the assemble message
  order system → memory_notes → summary_notes → skill_notes → elision →
  turns, rendered as `"Skill: <name>\n<description>\n<body>"` — AC1's
  byte-identity records the chosen rendering.
- Byte-bound governance beyond the 8192 in-slice bound = a recorded carry
  (N4).
- **Fail-open asymmetry pinned (L8)**: the fail-closed lens sits next to the
  fail-open memory gather in the same `assemble/4` — memory notes at `:none`
  are INCLUDED (legacy debt, prompt.ex moduledoc D4 ruling) while skill
  notes at `:none` are EXCLUDED. Do not "unify" the two arms.

### D7 — tool ids (trivial)

`skill.set` / `skill.retract` / `skill.read` — the retract id names the
atom's operation (retraction-is-negation, not delete-a-blob).

### D8 — resolution dialect: `{"", "unknown_entity"}` verbatim (easy)

`skill.read` of an unknown skill AND of a retracted skill both resolve
`{"", "unknown_entity"}` — the B6 spelling byte-for-byte
(tool_executor.ex:384). One resolution dialect: retracted ≡ never-existed at
the tool surface (no history oracle — N5; the stream keeps the distinction
for audit), and cross-wiring stays testable without a new literal.
Retract-of-unknown-name is a RESOLUTION OUTCOME: no negation is minted,
spelled `{"", "unknown_entity"}`. Note: dangling negations are
door-admissible (L5 — `validate_target` requires only nonempty hex,
delta.ex:96-98), so D8's no-mint outcome is purely TOOL-BOUNDARY discipline;
out-of-band mints can pre-position negations that take effect when their
target later arrives (federation arrival order). The gate runs before
resolution, so retract-of-unknown reaches `unknown_entity` only when the
name is allowlisted but has no live fold.

### N1 — whitespace-name hardening at the tool boundary (easy, MANDATORY)

Substrate-verified: the validate floor (delta.ex:115-118) refuses only `""` —
a `"   "` name mints fine and would exact-match nearly every prompt. The
reject lives at the TOOL BOUNDARY: `skill.set` trims for the CHECK and
refuses whitespace-only names — reject, never repair (the stored name is
never normalized).

### D9 — THE BOOT SEAM (moderate — the slice's biggest find, verified live)

The memory tools are ONLY wired in the T14c determinism TEST boot
(`Map.merge(Action.registry(), ToolExecutor.memory_tools(...))`). Production
surfaces are blind: agent.ex `default_tools` gives a workspace boot
`Action.registry()` ALONE — no memory_tools (lib/kyber/agent.ex:78-83) — and
reactor.ex `start_engine` defaults to `stub_tools()` (a lone echo tool;
reactor.ex:442-443). A live boot cannot see `memory.read` and would be blind
to every skill tool; all three proposals' tests pass while the model stays
blind.

**The slice fixes the seam at the ATTACH surface (H4)**: the merge target is
`Agent.attach/1`'s `default_tools/1` (agent.ex:78-83) — the ONLY
workspace-aware surface in the repo (it is called NOWHERE in lib/ today). A
workspace attach boot's default tools =
`Map.merge(Action.registry(), ToolExecutor.memory_tools(store_fn))` +
`ToolExecutor.skill_tools(store_fn)` — the model sees `memory.read` and the
skill tools by default; the stub remains the no-workspace default. Blast
radius is clean (no registry-key collisions — Action.registry() is
fs.read/fs.write/fs.list/sh.run/http.get/http.post; tool_key_map/1 and
tool_specs/1 handle the merged map; the url/memory policy layers abstain on
skill ids by membership).

**Witness (binds the ATTACH surface)**: a workspace attach boot without
explicit tools advertises `memory.read` + `skill.read` in the model's tool
list (skill_boot_seam_test.exs) — and asserts the tool LIST, not
executability (L7; even after the merge, both boot paths default to
`Gate.new()` — fail-closed on every call).

**The reactor path gets a RECORDED CARRY — NOT in-slice**: the reactor has
NO workspace concept (reactor_opts/2 threads only
budget_cap/engine/test_pid/operator_seed, daemon.ex:534-542; start_engine
defaults to stub_tools, reactor.ex:441; executor_for defaults independently
to stub_tools, reactor.ex:491). Workspace threading through
daemon.reactor_opts + both reactor defaults is recorded, not built.

**Two blind-build failure modes the build must NOT do (H4)**: (a) witness
against the reactor path — start_engine never reaches the workspace
default, the witness fails; (b) patch only start_engine — the engine's tool
list advertises `skill_set` while the executor's registry lacks it, and
every call answers `"unknown tool skill.set"` (tool_executor.ex:425).

### D10/D11 — scaffolding pins (easy)

- **D10 write-emission/idempotence**: skill deltas emit like memory deltas —
  record-dedupe; a replayed write is absorbed, never re-applied. **Emission
  shape + timestamp discipline (M6)**: a `skill.set` write emits
  [gate_decision, skill_set, tool_result] wires in THAT order; the SkillSet

  D3's count-all version inflated by replays).
- **D11 genesis-first ordering**: the `skill_policy` epoch, like the memory
  epoch, is seeded before any skill write.
