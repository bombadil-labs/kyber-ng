# T14f — The Skills Seam: Procedural Memory

build, no blind taste). Parent: T14e (`0eeb16e` on provisional/t14). Rails:
carried.

## The framing (the user's correction — binding vocabulary)

**A skill is NOT a delta. A skill is a derived entity — a view over its delta
stream.** Deltas are the events: each one SETS a property (or retracts) of a
named skill — signed, content-addressed, timestamped by its triggering delta,
append-only. The skill itself — name, description, body, version — exists ONLY
as the fold. `skill.read` returns the fold; the skill lens loads folds; nothing
stores "a skill" as a blob. This is the T14c architecture: the prompt isn't
stored, it's assembled; the canon isn't stored, it's resolved; a skill is a
view over its deltas, like everything else.

**The set-vs-merge distinction (a design cell, not a default):** the memory
canon MERGES (merge-is-union — facts accumulate; the atom). A skill property
is a VALUE, so its fold SUPERSEDES, not merges: the latest `skill_set` delta
for a property wins by delta order; retractions negate. "Merge-is-union"
governs the fact layer; the skill view is last-set-wins. The rumble ratifies
this — it is a pin, not an assumption.

## The schema sketch (the rumble pins the cells)

- **The skill aggregate**: identified by NAME (the aggregate key — stable
  across updates; "greet-new-member" is the same skill through its versions).
  Properties: description, body, (metadata as the slice decides). Each property
  is SET by a `skill_set` delta (a new delta per property, or one delta setting
  the full current property set — a cell).
- **The fold**: `Skill.view(set, name)` — fold the name's deltas in order:
  latest `skill_set` per property wins; a retraction delta negates (the skill
  is :retracted/not-found); the store holds deltas, the view is derived on
  read. Deterministic (no wall-clock — deltas claim their triggering delta's
  timestamp).
- **Update lineage**: an update is a NEW `skill_set` delta (superseding). The
  stream is the history; the view is the current state; version is derived
  (a cell: count of set-deltas vs the latest delta's id).
- **Removal**: a retraction delta (retraction-is-negation — the atom). The
  stream retains everything; restoring a skill = retracting the retraction.
- **The gate**: `skill_policy` epochs — the T14c memory-gate family pattern:
  fail-closed when ungoverned (skill WRITES refuse), epoch-allowlisted writes,
  fork-aware (the `:none`/`:forked` arms precede decode — the T14d norm).
  Creating/updating/removing skills is a WRITE — governed by operator policy,
  not the agent's whim.
- **Use — two surfaces**: (a) `skill.read` — mirror of `memory.read`: gated,
  returns the FOLD; unknown/retracted skill → the not-found resolution (the
  B6 `unknown_entity` precedent); (b) the **skill lens** in prompt assembly —
  like the window lens: a deterministic salience match over the VIEWS'
  names/descriptions (never the raw streams), capped, so relevant procedures
  ride into context without bloating it.

## Open design cells (the rumble pins these)

D1 — skill_set delta shape: one delta per property vs one delta setting the
full property set (atomicity, lineage readability).
D2 — the fold's ordering authority: delta-order by what (timestamp? append
order? the store's sequence) — must be deterministic and fork-safe.
D3 — version derivation: count vs latest-delta-id vs explicit version property.
D4 — retraction granularity: whole-skill vs per-property retraction.
D5 — the skill_policy epoch schema: allowlist by skill name? by writer? the
memory-gate family mapping.
D6 — the lens: salience matching (exact-name? prefix? description-keyword?),
the cap (a number), and the fold-vs-stream input.
D7 — the gate's write surface: which deltas are gated (skill_set only? also
retractions? — a retraction is a write to the same aggregate).
D8 — the skill.read not-found resolution: mirror B6's `unknown_entity`
spelling or a skill-specific status.

## Acceptance criteria (shape)

AC1 — the fold: a skill's current view derives from its deltas (set,
supersede, retract) — deterministic, no wall-clock; the "skill is a view"
contract witnessed (a test that proves no blob exists — the view is empty
until deltas are folded).
AC2 — the gate: skill writes fail-closed ungoverned, epoch-governed otherwise,
fork-aware; the read side mirrors memory.read's gating.
AC3 — the lens: relevant skills ride into the prompt (capped, deterministic);
irrelevant ones don't.
AC4 — lineage: update + remove + restore round-trip; the stream is intact
throughout (auditability).
AC5 (live, if the slice grows a live surface) — otherwise the operational
gates stay as the regression net.

## Design resolution (converged plan)

The rumble (P1/P2/P3 → A1/A2/A3 → R1/R2/R3, `.adlc/rumble-t14f/`) converged
on every contested cell. The binding framing held throughout: **a skill is a
DERIVED ENTITY — a view over its delta stream — never a delta; skill
properties are VALUES, so the fold SUPERSEDES (latest set wins), unlike the
fact layer's merge-is-union.** The resolutions below are pins, not sketches.

### D1 — delta shape: FULL-SET `SkillSet` (easy)

One delta per write carrying the WHOLE property set: name, description, body,
plus an optional provenance pointer `source/{:delta, call, "triggered"}` —
the MemoryEntity precedent (genesis.ex:103-104). Partial per-property maps
are REJECTED: genesis has no map kind, and per-property folding tears views
no author wrote. Metadata: P2's optional JSON-string role is ADDED
(spec-licensed "metadata as the slice decides"); the fold ignores its
absence.

### D2 — fold ordering: the store's sequence (moderate)

Deterministic delta order = the store's append sequence, fork-safe via the
existing epoch machinery. Per-property supersede: the LATEST set-delta (by
that order) wins for each property; a retraction negates. No wall-clock
anywhere in the fold.

### D3 — version: count of ALL set-deltas (easy)

`version` is derived = the count of ALL the name's set-deltas —
retraction-immune: remove/restore keeps the version stable, and history is
never renumbered. (P3's live-only count rejected: it collapses on remove and
renumbers on restore.)

### D4 — retraction: delta-ID-targeted negation + RECURSIVE liveness (hard)

A retraction is a delta-ID-targeted negation of the head set-delta — never
positional name-targeting (policy.ex:177-182 negates delta-ids only; the
grammar has no name form). Liveness is RECURSIVE: a flat retracted-ids scan
cannot express restore (retracting the retraction), so the fold computes
liveness through the negation chain. No retraction-path rollback: rollback =
a NEW superseding set (forward-only). Absorbed legs:

- **N7**: multi-removal + restore witnesses — existential inertness (every
  unretracted removal must be negated before the skill lives again;
  double-remove/single-restore leg).
- **N3**: re-creation beats revival — a fresh `skill_set` after a retraction
  is a NEW lineage; the retraction stays in the stream for audit; re-created
  properties beat revived ones with no special case.

### D5 — the gate: REUSE the memory-family `allow_entity` context (easy)

`skill_policy` reuses `allow_entity` `{:entity, name, "writable"}` — ZERO
genesis change (genesis.ex:84-87, policy.ex:141); the family "skill"
disambiguates skill entities from memory entities. Epoch arms precede args
decode (the T14d norm):

- ungoverned → refuse `skill_policy: no governing epoch (fail closed)`
- forked → refuse `skill_policy: epoch forked (fail closed)`
- governed → allowlist check.

Write surface (N6): `skill.set` AND `skill.retract` are BOTH gated — a
retraction is a write to the same aggregate. `skill.read` is gated like
`memory.read`.

### D6 — the lens: fail-closed born-here (hard)

The lens is a call-less content surface born this slice, so it is FAIL-CLOSED
from birth (N2 absorbed; the T14e url closure is the precedent — prompt.ex's
legacy epoch-blindness is not the norm): ungoverned AND forked ⇒ NO skills
ride; only epoch-filtered folds are eligible. NO GateDecision is emitted —
the lens is prompt assembly, not a gate.

- **Query scope**: the LAST USER TURN only (full-window scanning re-injects
  stale procedures; the negative leg's power).
- **Match**: exact-name tier (case-sensitive) FIRST, then `Assoc.digests`
  overlap ≥ 1 shared digest (assoc.ex:46-57 — CALLED, never re-implemented;
  one tokenizer discipline, no second dialect).
- **Cap**: 4 skills AND 8192 note bytes, SKIP-WHOLE — a skill that would
  blow the byte bound is omitted entirely, never truncated (selection, not
  repair). Deterministic under the total rank.
- Byte-bound governance beyond the 8192 in-slice bound = a recorded carry
  (N4).

### D7 — tool ids (trivial)

`skill.set` / `skill.retract` / `skill.read` — the retract id names the
atom's operation (retraction-is-negation, not delete-a-blob).

### D8 — resolution dialect: `{"", "unknown_entity"}` verbatim (easy)

`skill.read` of an unknown skill AND of a retracted skill both resolve
`{"", "unknown_entity"}` — the B6 spelling byte-for-byte
(tool_executor.ex:384). One resolution dialect: retracted ≡ never-existed at
the tool surface (no history oracle — N5; the stream keeps the distinction
for audit), and cross-wiring stays testable without a new literal.
Retract-of-unknown-name is a RESOLUTION OUTCOME: no negation is minted,
spelled `{"", "unknown_entity"}`.

### N1 — whitespace-name hardening at the tool boundary (easy, MANDATORY)

Substrate-verified: the validate floor (delta.ex:115-118) refuses only `""` —
a `"   "` name mints fine and would exact-match nearly every prompt. The
reject lives at the TOOL BOUNDARY: `skill.set` trims for the CHECK and
refuses whitespace-only names — reject, never repair (the stored name is
never normalized).

### D9 — THE BOOT SEAM (moderate — the slice's biggest find, verified live)

The memory tools are ONLY wired in the T14c determinism TEST boot
(`Map.merge(Action.registry(), ToolExecutor.memory_tools(...))`). Production
surfaces are blind: agent.ex `default_tools` gives a workspace boot
`Action.registry()` ALONE — no memory_tools (lib/kyber/agent.ex:78-83) — and
reactor.ex `start_engine` defaults to `stub_tools()` (a lone echo tool;
reactor.ex:442-443). A live boot cannot see `memory.read` and would be blind
to every skill tool; all three proposals' tests pass while the model stays
blind.

**The slice fixes the seam**: a workspace boot's default tools =
`Map.merge(Action.registry(), ToolExecutor.memory_tools(store_fn))` +
`ToolExecutor.skill_tools(store_fn)` — the model sees `memory.read` and the
skill tools by default; the stub remains the no-workspace default. Witnessed:
a boot-without-explicit-tools leg asserting `memory.read` (and `skill.read`)
appear in the model's tool list (skill_boot_seam_test.exs).

### D10/D11 — scaffolding pins (easy)

- **D10 write-emission/idempotence**: skill deltas emit like memory deltas —
  record-dedupe; a replayed write is absorbed, never re-applied.
- **D11 genesis-first ordering**: the `skill_policy` epoch, like the memory
  epoch, is seeded before any skill write.
