## The slice

The agent's actions are governed. Three carries close here:
- **URL policy** (SSRF-open, T12 #4): HTTP actions carry a policy — schemes/hosts checked
  BEFORE any request; a refused URL never touches the network.
- **Policy epochs** (boot-frozen policy, T12 #5): policy can evolve WITHOUT restart —
  policies are store claims; each policy is an epoch; revocation is NON-RETROACTIVE (a
  decision made under epoch 1 stands even when epoch 2 supersedes it).
- **Idempotence enforcement** (documented-not-enforced, T12 #3): a duplicate ToolCall
  (same content-derived id) executes ONCE; the duplicate is absorbed and observed, never
  re-executed.

In scope: the policy claim shape + epoch semantics, the URL gate in the http action path,
the idempotence gate in the tool-execution path, and their refusal routing through the
closed "decides" loop (hosted, never rebuilt — the T14a reactor already routes refusals).
Out of scope: prompt-answer-as-delta + memory-read seam + operator-key boot wiring
(T14c), boundary enumeration + precision bounding (T14d), the M5 engine verdict fix (the
slice owning the engine's decides path — recorded, not fixed here, avoided by config).

## Acceptance criteria (draft — the rumble pins the exact shapes)

- AC1 (URL policy): a policy claim in the store gates an http action — an allowed URL
  executes (a request is recorded); a refused URL is refused with a policy GateDecision
  routed through "decides", and NO request is made (asserted, not assumed).
- AC2 (epochs): a second policy claim supersedes the first; the gate consults the CURRENT
  epoch; a decision made under epoch 1 stands (non-retroactivity asserted in the test);
  revocation means the current epoch changes, not that history is rewritten.
- AC3 (idempotence): a duplicate ToolCall executes once; the duplicate is observed
  (dedupe record), never re-executed — the side effect (e.g. an http request) happens
  exactly once across the original + duplicate.
- AC4 (live, @tag :operational): a real model turn triggers an http action — allowed URL:
  request recorded, machine-checked (request body, never answer content); refused URL:
  policy refusal, no request. (Tool-less or tool-bearing per the live config — the M5
  avoidance discipline applies.)
- AC5 (determinism): policy decisions derive from store state; epoch resolution is
  content-derived; no wall-clock in decisions.

## Open decisions the rumble must pin

1. Policy claim shape: what a policy claim IS in the store (kind, pointers, target,
   content — an allowlist? denylist? patterns? per-host schemes?).
2. Epoch semantics: how an epoch derives from store state, what "current" means, the
   exact supersession rule, and the non-retroactivity guarantee's test shape.
3. URL gate placement + shape: in the http client? the tool executor? a reactor handler? —
   the exact check (schemes, hosts, patterns, defaults when NO policy claim exists) and
   the refusal shape (verdict/policy strings riding the canonical carry).
4. Idempotence gate placement + shape: the engine's tool loop? the executor? — the dedupe
   record (a claim? an observation? state?), and how a duplicate is answered (refused?
   acked? silently absorbed?).
5. Reactor/gate integration: the policy gate vs the oracle gate — same "decides" loop,
   layered, or unified? (The reactor hosts; the loop is closed; do not rebuild.)
6. Back-compat: existing boot opts, the engine's existing gate surface, the http
   client's current URL handling — unchanged or extended, never broken.
7. The deterministic tests: exact seeding + per-AC anti-placebo shapes (how each test
   FAILS when the feature is absent) + the AC4 live shape.
8. Deliverables: module/test file names (deliverable-existence gate).
