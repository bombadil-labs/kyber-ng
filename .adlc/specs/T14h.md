# T14h — Always-On Context: Continuity Beyond the Last Prompt

Status: OPEN (light ceremony — rumble for the design cells, one deterministic
build). Parent: T14g (identity — in rumble). Rails: carried.

## The framing

The user's brief: "context injection can't just be ad hoc memories and skills
related to the last prompt, there has to be a larger form of continuity going
on. Be creative."

Today the assembled prompt is: [identity block (T14g), memory_notes (the
lens over the last turn), skill_notes (the lens over the last turn),
summary_notes, elision, turns]. Everything except the identity block is
LAST-PROMPT-LOCAL: the lenses match the current turn; the window elides the
head into summaries. There is no LARGE-SCALE continuity — nothing that
answers "what has this agent been doing for the last week" unless a lens
happens to match.

ALWAYS-ON context = the set of store-derived artifacts that ride EVERY
prompt regardless of the last turn's content. The design question is WHAT
qualifies and HOW it's derived — deterministically, capped, and without
becoming a wall of noise that eats the window.

## Candidate always-on surfaces (the rumble pins the set)

- **A1 — standing memory**: the epoch-visible canon's "long-term" subset —
  memory entities with a `standing` flag or the canon's head entities
  (per-entity-latest), folded as a standing block. (The T14c memory canon
  merges; the always-on block wants the STANDING subset, not everything.)
- **A2 — the trajectory**: a compact digest of recent activity — the last N
  prompt/response pairs (not the raw turns — the window already does that)
  but a DERIVED digest: what was asked, what was done, what was decided.
  Rendered from the store's delta stream (the reactor's prompts + tool
  results), deterministically.
- **A3 — open threads / standing intents**: derived from the delta stream —
  requests without their completion, retractions pending, etc. (a "state of
  the world" digest).
- **A4 — the identity fold's dynamic half**: profile-scoped facts the agent
  has learned (the user's preferred greeting, the channel's norms) — the
  agent-writable counterpart to the operator-attested identity primitives
  (T14g G7).
- **A5 — cross-session persistence**: the summaries (conversation_summary
  deltas) promoted from elision-fodder to an always-on digest when the
  session is long-lived.

## The mechanism (the creative part — the rumble decides)

Options for HOW the always-on block is derived:
- **Option 1 — a standing-fold**: like the memory canon but for the standing
  subset; the block = fold + digest, recomputed per assembly, {timestamp, id}
  deterministic, byte-capped.
- **Option 2 — a periodic digest delta**: the reactor emits a
  `StandingDigest` delta at a cadence (tick-based), so the always-on block
  is a READ of the latest digest, not a fold per prompt. The digest is a
  VIEW over the stream, materialized on a schedule (the store only learns —
  digests are deltas too, superseding).
- **Option 3 — hybrid**: standing memory is a fold (fresh every assembly);
  the trajectory/threads are a digest delta (materialized by the reactor
  when the store changes, or on a tick).

The always-on block sits between the identity block and the memory_notes in
Prompt.assemble — the order: [identity, always-on, memory_notes,
skill_notes, summary_notes, elision, turns]. Capped (byte bound — the
rumble pins the number; the T14f lens cap is the precedent: 8192 skip-whole).

## Constraints

- Determinism: everything {timestamp, id}-ordered; no wall-clock in the
  fold (digest deltas may claim their tick's timestamp — a cell).
- The atom: digests are deltas (supersede), never ephemeral.
- The gate: what the always-on block MAY include is epoch-bounded (the
  profile's visibility — T14g's G4); a channel profile's always-on block
  must not leak broader memory.
- Fail-closed: an ungoverned profile gets NO always-on block (or the
  standing subset only — a cell).

## Open design cells

H1 — the always-on surface set (A1-A5: which, what qualifies as "standing").
H2 — the mechanism (fold vs digest-delta vs hybrid; the digest cadence and
timestamp discipline).
H3 — the always-on block's shape: order, byte cap, rendering (a cell:
"Standing memory:" header + digest lines?), the elision interaction (does
the always-on block change what the window elides?).
H4 — standing-qualification: what makes a memory entity "standing" (a flag
in the entity delta? recency? the epoch allowlist?).
H5 — the trajectory digest: what it includes (last N prompt/result pairs?
decisions only?), the cap, and how it differs from the window + summaries.
H6 — profile interaction: the always-on block under a channel profile
(subset + no broader-memory leakage — the AC).
H7 — the digest's write path: who mints StandingDigest deltas (the
reactor's tick? the store-change observer?), the gate on digest writes.
H8 — cost control: the always-on block vs the window budget — how the cap
and the digest cadence keep the prompt from bloating.

## Acceptance criteria (shape)

AC1 — the always-on block rides every prompt (the standing subset is present
regardless of the last turn's content); deterministic.
AC2 — the trajectory digest reflects recent activity (asked/done/decided)
and is capped.
AC3 — profile isolation: a channel profile's always-on block excludes
broader memory (leakage witnessed ABSENT).
AC4 — the block is byte-capped and the window's budget is preserved (no
bloat — the cap's skip-whole semantics witnessed).
AC5 — determinism: the fold/digest is {timestamp, id}-ordered,
replica-identical.

## Deliverables (shape)

- the standing-fold + always-on block in Prompt.assemble
- the digest delta family (if Option 2/3) + genesis evolution (the H5
  lesson — unknown types admit :raw)
- the trajectory renderer
- tests: always_on_test.exs, trajectory_test.exs, profile_isolation (with
  T14g's), determinism legs
