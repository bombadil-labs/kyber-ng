# T16 — Incremental, federatable indexes over the append-only store

## Purpose
Two things at once, both surfaced by the PR #5 round-5 adversarial review:

- **Close the O(N³) dedup regression.** `Kyber.Channel.Socket.open_duplicate?/1`
  answers "is this `ctl send` a re-send?" by nested full scans over
  `DurableStore.set()` — `message_answered?` and `inference_answered?` each
  re-scan the whole append-only log, so the cost is O(N³) per incoming
  message and grows with the agent's lifetime. For a long-lived daemon this
  blocks the socket GenServer on every send.
- **Stand up the indexing substrate the substrate is missing.** The store is
  an append-only log with no query layer; dedup is only the *first* historical
  question the agent will ask (memory seam, always-on context, hyperviews all
  need "what points at X?" answers). Build the index as a **first-class,
  spawnable thing**: an incremental index maintained at the one append
  chokepoint, plus a generic `IndexServer` GenServer you can spin up **per
  container / per hyperview** — the rhizomatic seam. A default dedup view
  rides the same machinery.

Concretely:

- **F1 — incremental dedup index (in-process).** `DurableStore` maintains a
  dedup index in its own GenServer state, updated exactly once per admitted
  delta at the `do_append` chokepoint (the store already serializes every
  append and owns `state.set`). `open_duplicate?/1` reads that index in O(1)
  instead of scanning. Closes the round-5 medium.
- **F2 — append feed / subscribe seam.** `DurableStore` broadcasts each
  admitted delta (id + parsed claims) to a set of subscriber pids. This is
  the rhizomatic door: anything that wants a view of the log subscribes once
  and receives every delta in commit order, no polling `set/0`.
- **F3 — `IndexServer`, spawnable per container / per hyperview.** A generic
  GenServer that holds its own `DurableIndex` view, fed by the F2 feed. Spin
  up one per container, per hyperview, per differently-tuned query — each is
  an isolated process maintaining its own derived map. The default dedup view
  is one such instance (or the in-process F1 index when no subscribers are
  configured).
- **F4 — `DurableIndex` pure module.** The index *logic* (new / add_delta /
  answered? / by_pointer) is a pure, side-effect-free module reused by both
  the in-process store index (F1) and every spawned `IndexServer` (F3). This
  is the reusable unit the rhizome forks.

## Why now
PR #5 is merged: Wisp runs, dedup is order-independent and retry-safe, the
no-key boot warns. The round-5 judge passed the gate but flagged the O(N³)
dedup scan as a scaling debt. That debt is a *symptom* — the substrate has no
index layer at all, and every future "what points at X?" question (memory
seam T14c, always-on context T14h, hyperviews) will reinvent the same scan.
Building the index as a spawnable, federatable primitive now pays the dedup
debt AND gives the later slices their query substrate in one move.

## Acceptance (AC)
- **AC1** `DurableStore` maintains a dedup index in `state`; `open_duplicate?/1`
  no longer calls `DurableStore.set()` to answer. A `ctl send` of content
  matching a *recent unanswered* `MessageReceived` still collapses; an
  answered re-ask and a *stale* failed-turn re-send still behave exactly as
  T15c specifies (the round-3 + round-4 behavior is preserved).
  > Verified by `test/kyber/t15c_send_dedup_test.exs` (the existing AC1
  > double-tap-collapse, AC-reask-allowed, and round-4 retry-then-answer
  > tests all stay green; a new test asserts `open_duplicate?` does NOT call
  > `DurableStore.set/0` — gated via `:meck`/call-count or a store-side flag).
- **AC2** `DurableStore.subscribe/1` registers a pid; each admitted delta is
  delivered to subscribers (cast) in commit order, exactly once per append,
  only after the write-ahead commit lands (same ordering guarantee as the
  existing reactor `notify_reactor` pin-1 seam).
  > Verified by a new `test/kyber/durable_store_test.exs` case: a subscribed
  > test process receives one `{:delta, id, claims}` cast per appended delta,
  > in order, and never receives a delta the door refused.
- **AC3** A spawned `IndexServer` (dedup view) fed by the F2 feed answers
  `answered?/1` identically to the in-process index, and survives a store
  restart by replaying the log (the store re-derives the index from the
  replayed `set` on boot, so a freshly spawned view can be seeded from
  `DurableStore.set/0` on start).
  > Verified by a new `test/kyber/index_server_test.exs`: spawn a dedup
  > `IndexServer`, append a `MessageReceived` + `InferenceRequested` +
  > `ResponseDelta` via the store, assert the server reports the message
  > answered; restart the store from the same log and assert a re-seeded
  > server agrees.
- **AC4** The dedup index and any spawned `IndexServer` are **append-only,
  union-merge** derived state — they add on admit, never mutate or remove
  (retraction is itself a delta the feed delivers; the index chooses to
  ignore or fold it). No index entry is ever deleted, matching the
  "store only learns" atom. The dedup index is bounded (only
  `MessageReceived`/`InferenceRequested`/`ResponseDelta` kinds contribute).
  > Verified by `test/kyber/durable_store_test.exs` (append N deltas, assert
  > index size grows monotonically, equals the count of indexed kinds, and a
  > refused delta does not change the index).
- **AC5** Full suite stays green at the pre-existing baseline (631 tests, 1
  known flake `trajectory_test`); the live Wisp boot + `ctl send` round-trip
  is unchanged in latency class (O(1) dedup vs O(N³)).
  > Verified by `mix test` (baseline) + a live `ctl send` against the booted
  > Wisp daemon (operational check, like `reactor_operational_test.exs`).

## Out of scope
- A general query DSL / pointer-graph query language over the store. This
  slice builds the *index primitive + the feed + one dedup consumer*. Richer
  hyperview queries are a later slice (T15e or a T14k-style substrate spec).
- Materialized hyperviews beyond the dedup view (the spawnable server exists;
  only the dedup view is shipped as a consumer this slice).
- Reindexing on retraction beyond "ignore the negation delta" — full
  retraction-aware index folding is noted as a future capability, not built.
- Any change to `deps/`, `spec/`, `mix.exs`, `config/` (frozen). No new
  `DeltaSet` wire format; the index is pure in-memory derived state.

## Design notes (resolution)
- Chokepoint: `DurableStore.do_append/2` is the single serialized append path
  (`handle_call({:append, wire})` → `Store.admit` → persist → merge into
  `state.set`). The new delta is the one key in `candidate_set` not in
  `state.set`; extract `{id, claims}` from it and call
  `DurableIndex.add_delta/3` once. No rescan of the whole log on append.
- `DurableIndex` (pure, `lib/kyber/durable_index.ex`): holds
  `%{messages: %{id => {content, ts}}, inf_by_prompt: %{prompt_ref => true},
  resp_by_request: %{request_ref => true}}`. `add_delta(index, id, claims)`
  inspects `claims.pointers` (string-keyed JSON profile:
  `target` is `%{"delta" => hex}` / `%{"id" => entity}`) and updates the
  right map. `answered?(index, msg_id)` = `Map.has_key?(inf_by_prompt,
  msg_id) and Map.has_key?(resp_by_request, msg_id)`. This is the corrected
  two-hop bridge the round-5 fix needs (requestRef points at the *inference*
  id, not the message id — the bug that broke the first attempt).
- `IndexServer` (`lib/kyber/index_server.ex`): GenServer holding a
  `DurableIndex`. `start_link(opts)` optionally seeds from
  `DurableStore.set/0` (boot replay). Handles `{:delta, id, claims}` casts
  from the F2 feed (calls `DurableIndex.add_delta`). Exposes
  `answered?/1`, `by_pointer/2` (the generic query hook future views use).
- `DurableStore`: add `state.index` (F1 in-process) + `state.subscribers`
  (F2 pids). `subscribe/1` appends to subscribers; `do_append` (after commit)
  calls `DurableIndex.add_delta` on `state.index` AND `GenServer.cast`s each
  subscriber `{:delta, id, claims}`. `DurableStore.dedup_check(content)`
  reads `state.index` O(1) (the default path); when subscribers are present
  the dedup answer can also be served by the named `IndexServer`.
- `socket.ex`: `open_duplicate?/1` becomes `not DurableStore.dedup_check(content)`
  (plus the `@dup_window_ms` recent-prune, which the index stores ts for).
  Remove the now-dead nested `message_answered?`/`inference_answered?` scans
  (keep the shared `delta_id`/`pointer_target`/`message_received?`/
  `content_of` helpers if still referenced; otherwise trim).
- Replay: `init` builds `state.index` from the replayed `set` in one pass
  (the log is already classified by `replay/1`); spawned `IndexServer`s seed
  from `DurableStore.set/0` on `start_link`.
- No `Process.sleep` in tests; `assert_receive`/cast-count for F2/F3.

## Premortem (folded — 2026-08-12, from live PR #5 + T16 spike)

Mechanistic failure modes surfaced before implementation; the design above already
closes each. Recorded so the build does not re-litigate them.

- **PM1 (HIGH) — the two-hop `requestRef` bridge.** A `ResponseDelta`'s `requestRef`
  points at the *inference's* delta id, NOT the message id. The naive single-map fix
  (`inf_by_prompt` keyed by `promptRef`/`msg_id`, `resp_by_request` keyed by
  `requestRef`) then checks `msg_id == requestRef` — which never matches, so
  `answered?` is permanently false (every message looks unanswered → re-sends wrongly
  collapsed). Correct shape: `inf_by_prompt :: prompt_ref => [inference_ids]`;
  `answered?` = any inference_id for this message has a `ResponseDelta`
  (`resp_by_request :: inference_id => true`). The spec's `answered?` already encodes
  this; the implementation MUST keep the inference-id as the bridge, not collapse the
  two maps into one key match. (This exact bug broke the first round-5 fix attempt.)
- **PM2 (MEDIUM) — dead append vs live append ordering.** The index update must run
  ONLY after the write-ahead commit lands (persist succeeded), mirroring the existing
  `notify_reactor` cast (pin-1 seam). Updating the index before persist, or on a
  `persist_failed` reply, desyncs the index from the durable set (index claims a delta
  the log does not have → false "answered" / wrong dedup). Fix: update index +
  broadcast subscribers inside the `{:ok, new_state}` branch of `persist_then_merge`,
  never on the `{:error, :persist_failed}` branch.
- **PM3 (MEDIUM) — replay must rebuild the index identically to live append.** On boot,
  `init` replays the log; `state.index` must be reconstructed from the replayed `set` in
  the SAME order/shape as live appends, or a freshly spawned `IndexServer` seeded from
  `DurableStore.set/0` will disagree with the in-process index (AC3). Fix: both paths
  call the same `DurableIndex.add_delta/3`; no separate code path for replay.
- **PM4 (MEDIUM) — subscriber fan-out blocks the append hot path.** `do_append` runs in
  `handle_call`; `GenServer.cast` to each subscriber is async (non-blocking) — fine —
  but the subscriber list must be bounded and the cast must never raise (a dead
  subscriber pid must be pruned, not crash the store). Fix: trap exits / prune on
  `cast` failure; subscribers are a small registered set, not unbounded growth.
- **PM5 (LOW) — index memory growth.** The index stores per-delta derived maps; for a
  long-lived daemon these grow with the log. Acceptable this slice (bounded to 3 delta
  kinds; the message map can be pruned by `@dup_window_ms` TTL later). Not a blocker;
  noted so a future slice adds TTL pruning rather than letting it grow unbounded.
- **PM6 (LOW) — retraction is a delta the feed delivers.** A retraction (negation)
  delta arrives via the feed like any other; the index must NOT try to "delete" the
  original (the store only learns). Fix: `add_delta` ignores retraction deltas for the
  dedup view (out of scope: retraction-aware folding). Documented in AC4 / Out of scope.
