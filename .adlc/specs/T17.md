# T17 — Agent identity as a delta-folded entity (spin up an agent by name)

## Purpose
Today a kyber agent's *operational identity* is a bag of CLI flags assembled at
boot: `--model`, `--base-url`, `--api-key-env`, `--operator-seed-env`,
`--oracle-seed`, `--system-prompt`, `--channel-socket`, `--loop`, `--keyring`,
`--log`. T15 proved the mechanics; the ergonomics are still one long command per
boot, and nothing about *who the agent is* survives between boots.

T17 makes **an agent an entity folded over its own delta stream** — the house
doctrine (deltas SET properties; facts merge; values supersede, last-set-wins;
**retraction is negation**). The agent's operational identity (soul, provider,
model, key env, prompts, seed policy) lives as `AgentSet` deltas in the agent's
own store. There is **no reified config file**: the delta stream is the ONLY
source of truth, every mutation goes through a delta-generating interface, and
**config is hot-swappable** — a delta takes effect on the next inference cycle,
with an automatic retraction harness (last-known-good) as the safety net.

    kyber agent new wisp --soul "I am wisp, the quiet sibling."   # store + seed AgentSet delta
    kyber agent list / show wisp                                  # fold the head, print it
    kyber daemon --agent wisp                                     # boot: store -> fold -> boot opts

## Why no config file (the divergence argument)
A reified JSON file is a **second source of truth with editable surface** — a
human will edit it, and then the file and the delta stream disagree, with no
principled resolution. The wire format is already JSON; portability is delta
export/import, not a view dump. Therefore:

- **Inspection** = `kyber agent list` / `show <name>` folding and printing
  (stdout, no file).
- **Portability** = export/import the DELTAS (Federation.export/import wire
  format — clone an identity by replaying its `AgentSet` stream into a new
  store, same fold, byte-identical view).
- **Editing** = only through delta-generating verbs (below).

## The only write paths: mutation surfaces
Every mutation is an `AgentSet` delta append. Three surfaces, all existing or
trivial extensions of existing seams:

1. **Operator CLI verbs** (no daemon needed — open the store, append, like
   `kyber ingest`): `kyber agent new`, `agent set <name> <field> <value>`,
   `agent set-soul`, `agent unset <field>`. Each appends an operator-attested
   `AgentSet` delta carrying only the changed fields (SET semantics).
2. **The served channel** (daemon up): a `set-config` verb on the channel
   socket JSONL protocol (`kyber ctl --log <path> set-config {...}`), spoken
   by the existing ctl client. Operator-attested (the ctl's operator seed) —
   the same door as `send`.
3. **The agent itself** (opt-in): when the live head is `self_config: true`,
   the agent's own tool surface (the reactor's tool executor) gains a
   `self_config.set(...)` tool that appends AGENT-authored `AgentSet` deltas.
   Agent-authored deltas are **fold-inert by default** (H2c author filter,
   mirroring ProfileSet) — the opt-in grant flips the fold to accept the
   agent's own stream, same last-set-wins.

There is no other write path. No file editing, no parallel truth, no
import-that-isn't-a-delta.

## The delta (schema, v1)
A new declaration delta `AgentSet` (content-addressed like ProfileSet):

```json
{
  "type": "AgentSet",
  "name": "wisp",
  "soul": "I am wisp, the quiet sibling — grounded, honest, eager.",
  "provider": {
    "base_url": "https://api.deepseek.com/v1",
    "model": "deepseek-v4-flash",
    "api_key": {"env": "DEEPSEEK_API_KEY"} | {"enc": "<base64 nonce||ct||tag>"}
  },
  "system_prompt": "optional override; absent => kyber default",
  "operator_seed_env": "WISP_OPERATOR_SEED",
  "oracle_seed": "present" | "absent",
  "loop": "reactor" | "ack",
  "channel_socket": "default" | "<path>" | null,
  "profile": "wisp" | null,
  "self_config": false
}
```

(`provider.api_key` is a tagged union: `{"env": NAME}` references an env
var; `{"enc": ...}` is a key value encrypted at rest (AC20). The operator
seed is NEVER a delta value — it is the root secret, env-held only
(AC21); it unlocks the others at the usage point.)

`AgentSet` deltas **SET properties** — each delta carries only the fields it
changes; the fold merges per-field with last-set-wins (facts merge, values
supersede). `name` is the fold key; the live head is the latest
operator-attested delta for `name` (ProfileSet's `{timestamp, id}` order
within author, latest-wins). A field absent from a delta is untouched;
`agent unset` appends a delta setting the field to its default/absent value.

**Dedup is SEMANTICS-AWARE (premortem P1-fold):** content-derived identity
plus naive dedup breaks re-assertion (`set A → set B → set A` would
content-address the third write to delta1's ID, dedup absorbs it, no new
delta exists, and last-set-wins still resolves to B — `agent set` reports
success while `show` disagrees). Dedup therefore absorbs a delta only when
its resolved value EQUALS the current fold — re-asserting the current value
is a true no-op, but re-asserting a PREVIOUS value (a genuinely different
fold state) must produce a new delta that re-wins the merge. The
timestamp is part of the delta's content address for this reason.

**Retraction (the D5 verdict):** the substrate atom `retraction-is-negation`
applies to `AgentSet` exactly as it does to ProfileSet — a retraction delta
pointing at a target `AgentSet` delta negates it, and the fold steps back to
the **previous live head** (last-known-good). This is the safety harness's
mechanism: a bad config change is retracted, the fold re-derives, and the
agent keeps running on the last head that worked. The retracted delta stays in
the log (the store only learns); negation is a fold-time operation.

The **H2c author filter** applies exactly as in Profile: agent-authored
`AgentSet` deltas are fold-inert unless the live operator-attested head says
`self_config: true`. **The grant is PROSPECTIVE (premortem P1-fold):** an
agent-authored delta folds only if appended AFTER the operator-attested head
that granted `self_config` (compare `{timestamp, id}` against the grant
delta) — a pre-grant agent delta stays inert forever, so flipping the flag
never retroactively activates a backlog of stale agent writes (e.g. an old
provider change targeting a decommissioned endpoint suddenly hot-swapping the
live daemon). A retraction authored by the agent can only negate deltas its
own stream folded in (it cannot negate operator-attested changes).

## Defaults as the genesis layer (the D7 verdict)
**A default configuration is just the FIRST delta in the stream.** When
`kyber agent new <name>` creates a store it appends, in order:

1. **The genesis default `AgentSet` delta** — the built-in fallback layer,
   always the same: `provider: {base_url: api.deepseek.com/v1, model:
   deepseek-v4-flash, api_key_env: DEEPSEEK_API_KEY}`, `oracle_seed: absent`,
   `loop: reactor`, `channel_socket: default`, `self_config: false` (the
   operator may omit any of these via `--` overrides at `new` time, in which
   case the default delta carries the built-in values).
2. **The operator's seed delta** — the `--soul/--model/--base-url/...` flags
   as a SECOND `AgentSet` delta (SET semantics: only the fields the operator
   actually named; everything else stays at the genesis layer).

The fold is last-set-wins per field, so the **layering is the ordering**:
the genesis layer provides the fallback, later deltas override. No
default/override distinction exists in the fold — a delta is just a delta,
earlier = default, later = override.

Consequences, all free:

- **The deepseek fallback is always already there.** Wire wisp to claude via
  an override delta; if it fails, the harness retracts it (AC12) and the
  step-back lands on the genesis layer — deepseek, untouched and tested.
- **Unsetting a default = retracting the genesis delta.** The operator
  `agent retract <genesis-delta-id>` negates the default layer itself; the
  fold then has no head for `name` and boot falls through to the engine's
  hardcoded defaults (deepseek-v4-flash), exactly like an agent with no
  `AgentSet` at all.
  Negation is the unset — no special "default" code path.
- **The harness never auto-retracts the genesis layer.** Auto-rollback
  (AC12) is bounded and only ever steps back through AGENT-authored
  self-config deltas (and the most recent operator override on explicit
  operator action). The default layer is operator-attested; only an explicit
  operator `agent retract` can remove it.
- **Genesis is validated at new-time (premortem P1-fold).** The built-in
  fallback is NOT assumed healthy: `agent new` checks the genesis layer's key
  env is present (AC18 path) and the model id is known, and refuses to create
  an agent whose fallback is born broken. The terminal step-back state is the
  ENGINE's deepseek defaults (never a possibly-dead genesis delta) — a dead
  fallback cannot brick the harness.
- **Templates are free later.** `agent new --from <export.jsonl>` (D2)
  replays a stream, so a "default-ish template" is just an export; and an
  operator can pre-provision `~/.kyber/agents/<name>` deltas (e.g. a
  `self_config: true` head) as an organizational default.

## Secret hardening (the D8/D9 verdict)
The delta store **never holds key values in the clear** — either env NAMES
(the M5/N4 discipline) or **encrypted-at-rest values** (D9). And secrets
**never ride the LLM prompt** as a rule. Two mechanisms, one rule:

**Mechanism 1 — env-name reference.** `provider.api_key = {"env":
"DEEPSEEK_API_KEY"}`. The value never exists in the store; it is resolved
from the environment at the usage point.

**Mechanism 2 — encrypted-at-rest (the D9 verdict).**
`provider.api_key = {"enc": "<base64>"}` where the payload is an AEAD
ciphertext of the key value, encrypted with a key **derived from the
operator seed** (HKDF-SHA256 with a `kyber:agent-config:v1` info label —
the seed is the agent's root secret, already env-held and required at
every usage point; no new master key to manage). Decryption happens ONLY
at the usage point (building the `LlmHandler` / API request): the
plaintext exists in that narrow, unlogged window, is never in daemon
state, never in `show`/`status`/`list`, never in the prompt, and never
re-enters the store. The ciphertext travels with the delta stream —
export/import/federation carry working credentials, and the store alone
is useless without the seed.

The hard boundary (root secret): the **operator seed itself is never a
delta value** — encrypted or not. It is the bootstrap: the store cannot
be read (and the ciphertext cannot be decrypted) without it, so it must
be env-held, never serialized. `operator_seed_env` is env-name-only.

The rules:

1. **Door validation.** A secret field value is either an env NAME matching
   `^[A-Z_][A-Z0-9_]*$` (`{"env": ...}`) or well-formed ciphertext
   (`{"enc": ...}` — valid base64, expected length/shape). A delta whose
   secret field is a PLAINTEXT key (a pasted `sk-...`, a long base64/hex
   run, `KEY=` pair) is **refused at the door** with a legible message:
   "provider keys are either referenced by env NAME (`--api-key-env
   DEEPSEEK_API_KEY`) or supplied encrypted (`--api-key-env` + the key in
   the daemon env / `--api-key` read from stdin, never argv)". Same
   validation on the genesis default and on `--from` imports (a malicious
   export cannot smuggle a plaintext key into the stream).
2. **Free-text fields (soul, system_prompt) get a secret-shape scan.** These
   fields legitimately ride the prompt — so a value containing an obvious
   secret shape (`sk-`, `api_`, ≥32-char base64/hex runs, a `KEY=...`/`=`
   pair with a long right side) is refused with the same repair message.
   False-positive risk is low (a soul rarely contains 32-char hex); the
   message names the alternative (reference by env name). The 8192 lens cap
   already bounds these fields.
3. **Keys are held as closures, never in inspectable state.** The resolved
   key value (from the env NAME) is captured at boot (M12 pattern — the
   Discord token precedent) and threaded into the `LlmHandler`; it is never
   part of daemon state, never serialized to the store, never in `status`/
   `show`/`list` output (those print the NAME only).
4. **A clean, legible error with repair instructions** when the named env
   var is unset/empty at boot:
   `agent wisp: provider deepseek needs the API key named by
   agent set wisp --api-key-env DEEPSEEK_API_KEY — export DEEPSEEK_API_KEY
   in the daemon's environment, then re-boot`. Never the key, never a
   traceback. This is a config-class failure (AC12 detection), so the
   harness treats it like any bad delta (bounded step-back to the genesis
   layer when it was an override).
5. **Secrets never ride the prompt, tested.** A test boots a `:reactor`
   daemon with a real env var set, assembles a prompt, and asserts the
   assembled context contains no key-shaped string (no `sk-`, no 32+ char
   high-entropy run, no `KEY=` pair). A second test asserts `status`/
   `show`/`list` and the store contain only the env NAME.
6. **Log redaction.** The daemon's log path redacts anything matching the
   configured key values (the values are known at boot from the closures);
   error messages never echo a key.
7. **Inference-boundary redaction (the D10 verdict — "at least").** Even
   with write-time refusal (1) and encryption-at-rest (2), a secret could
   in principle reach the assembled context (a tool output echoing an env
   var, a memory digest capturing a key, a soul that predates validation).
   The final layer: at the inference boundary — inside `LlmHandler`, in
   the unlogged usage window, immediately before the provider request is
   built — the context is scanned and **any occurrence of a known secret
   VALUE is replaced with `[REDACTED]`** before it can reach the wire.
   The known values are exactly the ones already in hand at the usage
   point: the resolved/decrypted `api_key`, the operator seed, and the
   derived config key. Exact-value matching (no false positives — the
   substrate's own 64-hex content IDs and `ed25519:` authors ride the
   prompt legitimately). A conservative shape-scan (`sk-`, `api_`,
   `AKIA`/`ghp_`/`xoxb` prefixes, `KEY=` pairs, `Bearer `) catches
   *unknown* secrets as a second belt — deliberately conservative to
   avoid nuking legitimate hex. Redaction is visible to the model
   (`[REDACTED]` marker, not a silent hole).
8. **Fail-closed entropy scan + tombstone runbook (premortem P3-fold).**
   The shape-scan will miss a secret in an unanticipated format — and in an
   append-only, export-replicating store, a miss is PERMANENT and
   FEDERATES. Two responses: (a) free-text fields (soul, system_prompt) get
   a fail-closed high-entropy scan in addition to the shape-scan (a
   long-random-string threshold, tuned so legitimate prose never trips it);
   (b) the spec ships a documented TOMBSTONE procedure for the inevitable
   miss: the operator retracts the offending delta, appends a
   `SecretTombstone` claim recording the exposure (delta id, field, time,
   rotated-key pointer), and rotates the credential — the runbook is part
   of the build, not discovered after the incident.
9. **`agent rekey` ships with `{enc}` (premortem P2-fold).** Rotating a
   compromised operator seed must not brick every ciphertext in the store:
   `agent rekey` decrypts under the old seed, re-encrypts under the new,
   and appends superseding deltas. The D2 clone-by-replay workflow states
   its seed story explicitly (AC20): a clone either receives the seed
   out-of-band (operator decision, documented) or re-provisions its
   `{enc}` values via `agent set` on the destination — cloning never
   silently depends on scp'ing the root secret.

v1 deliberately does NOT build a secret vault / external key manager — env
referencing is the primitive; a vault is a later slice (out of scope).

## Threat model (the honest boundary)
What encrypted-at-rest + usage-point decryption defends against, stated
precisely:

- **Passive leakage** — a stolen or exported store (ciphertext only), log
  dumps, `show`/`status` output, accidental inclusion of a key-shaped
  string in a soul/system_prompt/memory. All closed by AC17-AC21.
- **The agent's ordinary operation** — the agent never receives key
  values through its tool surface, its prompt, its memory, or the fold.
  The daemon holds the seed env-side; the agent's tools are gated by the
  existing tool bounds; the key material exists only in the unlogged
  usage-point window.

What it does NOT defend against — **an agent with unrestricted code
execution in the same OS domain can read any secret the daemon can read**
(the seed via `/proc/<daemon>/environ` or the keyring, then decrypt the
ciphertext; or simply read the env of the process making the API call).
No cryptographic construction changes this: if the agent can execute the
decrypt path, it can obtain the plaintext. The only true
impossibility is capability separation:

- **(a) sandboxed tool execution** — agent tools run as an unprivileged
  OS user / container with no access to the keyring, the daemon env, or
  the secret-derivation code path;
- **(b) off-box keys** — a local/remote proxy or KMS holds the keys and
  attaches them at the provider boundary; key material never exists on
  the agent's machine.

Both are architectural follow-ons, recorded in PLAN.md §2 backlog (not
this slice). Within T17, the honest claim is the narrow one: **secrets
never leave via the agent's normal operation**, and the design's defense
against a hostile agent is the existing governance dials (tool bounds,
H2c author filter, `self_config` opt-in) — trust the agent, or sandbox
it; crypto alone cannot chain it.

## Hot-swap (the D6 verdict)
Config is **hot-swappable**: a live daemon subscribes to its store's append
feed (the T16 subscribe seam) and watches for `AgentSet` deltas. When one
lands:

1. Re-fold the head (pure) and diff the resolved boot opts against the live
   engine's.
2. Changed keys are rederived on the **next inference cycle** (no reboot):
   rebuild the `LlmHandler` (model/base_url/api_key/system_prompt — T15
   already threads these), re-mint/supersede `identity:soul` (the always-on
   block picks it up next assemble), flip the oracle gate for the seed policy.
3. The first inference after a config delta is the **probe**: a
   config-class failure (per the harness classifier) triggers the safety
   harness.

**Overrides survive re-folds (premortem P2-fold).** CLI overrides (AC4:
`--model kimi-k3` without a delta) are PINNED in daemon state and re-applied
after EVERY re-fold — a hot-swap delta touching an unrelated field must not
silently drop an active override. `status` shows BOTH the fold value and the
live value when they differ, so `show` (fold) and `status` (live) can never
silently disagree. There is an explicit AC: "hot-swap delta lands while a CLI
override is active" — the override wins, is re-applied, and is visible.

## The safety harness (the D5 verdict, concretized)
The canonical failure mode the user named: the agent modifies its config, makes
a mistake, and the harness is bricked. The harness is automatic, bounded, and
loud. **Premortem-fold (P1): rollback is PER-FIELD, not per-delta** — the fold
is a per-field merge over the whole stream (there is no head pointer), so
"retract the most recent delta" could remove an innocent field while the
broken field (set N deltas ago) survives. The harness therefore operates on
*resolved fields*, never deltas:

- **Detection.** A config-class failure observed at boot OR on the first
  inference after an `AgentSet` delta. The classifier is EXPLICIT and
  exhaustive: config-class = HTTP 400/401/404 (bad model, bad base_url, bad
  key), missing env var, channel bind failure, decrypt failure. NOT
  config-class = 429/5xx/timeout (transient — retry with backoff, NEVER
  retract on transient; require N consecutive config-class failures before
  any step-back, so a provider brownout destroys no good deltas).
- **Step-back (per-field).** On a config-class failure, identify the resolved
  fields that changed since the last known-good inference; retract exactly
  the deltas that last SET those fields (one retraction per offending delta).
  If the failure persists, step back further — **bounded** (a small fixed
  budget of field-steps, then it stops and holds the oldest known-good-or-
  default head). The terminal state is the ENGINE's deepseek defaults, never a
  possibly-dead genesis layer.
- **Notification.** Every rollback emits a `ConfigRollback` claim (offending
  delta ids, reason, restored field values, timestamp) that surfaces in
  `ctl tail` / `status` and logs loudly. The user is always told. Auto-rollback
  applies to agent self-config deltas; for operator-attested deltas the same
  detection fires but rollback of an OPERATOR's change requires explicit
  operator action (`agent retract <delta-id>`) — the harness detects and
  notifies, it does not silently undo the operator. (The rollback loop itself
  is operator-seed-gated like `send`, M5.)
- **base_url is operator-attested ALWAYS (premortem P0).** The resolved key
  is never sent to an origin the operator has not attested: `base_url`
  changes fold only when operator-attested, regardless of `self_config`
  (a prompt-injected agent must not be able to point the daemon's key at an
  attacker proxy — the proxy-to-real-provider case never fires a failure, so
  the harness can't see it). An agent `self_config.set` of `provider` may
  change `model`/`api_key` but NEVER `base_url`; a `base_url` change is an
  operator-only verb, and any `base_url` delta logs loudly.

## The registry (bootstrap only)
The one irreducible filesystem artifact: a tiny pointer file
`~/.kyber/agents/<name>` (D1 verdict) containing `{log_path, keyring_dir}` —
enough to FIND the store before its deltas can be read. It is a directory
entry, not identity truth: it holds no model, no soul, no prompt. `kyber
daemon --log <path>` also boots directly (the store implies the identity);
`--agent <name>` is sugar over the pointer.

## Acceptance (AC) — draft
- **AC1** `kyber agent new <name> --soul "<text>" [--model ..] [--base-url ..]
  [--api-key-env ..]` creates the store at `<registry>/<name>/store.jsonl`,
  writes the seed operator-attested `AgentSet` delta (tmp-only store/keyring;
  never the real `~/.kyber`), and the registry pointer. Refuses to overwrite an
  existing agent without `--force`.
  > verify: store exists with an `AgentSet` delta; `agent list` shows it.
- **AC2** `kyber daemon --agent <name>` resolves the pointer, opens the store,
  folds the `AgentSet` head, and boots with model/base_url/api_key/
  system_prompt/soul/seed-policy from the fold — observed end-to-end: a live
  turn answers on the configured provider and `Soul: ...` renders in the
  assembled prompt (operational test, T15b path).
- **AC3** A fold with `oracle_seed: absent` boots refuse-only (the oracle gate
  blocks dispatch) exactly like today's flag-equivalent. `present` opens it.
  > verify: boot a `:reactor` daemon from a fold with `oracle_seed: absent`,
  > send a message, observe the GateDecision refuse; flip to `present`, send
  > again, observe the gate opens (operational test, T15b path).
- **AC4** CLI flags override the fold at boot: `kyber daemon --agent wisp
  --model kimi-k3` boots kimi-k3, not the head's deepseek. Overrides never
  append deltas.
- **AC5** The H2c filter holds: an agent-authored `AgentSet` delta is
  fold-inert when the head is `self_config: false` (or absent) — including a
  newer-delta-under-expected-name escalation attempt. With `self_config:
  true` on the operator head, the agent's own subsequent deltas fold — and
  the grant is PROSPECTIVE: a pre-grant agent delta stays inert forever
  (premortem fold). The flip-test is in the suite (same agent delta, head
  flag on vs off; pre-grant deltas never activate).
  > verify: the flip-test — same agent-authored delta folds with the grant
  > head present, stays inert with it absent; a delta appended BEFORE the
  > grant stays inert after the flip (never retroactively activates).
- **AC6** Boot mints `identity:soul` from the fold's `soul` field (idempotent
  — never re-mints over an existing soul). 8192 lens cap respected at render.
  > verify: boot twice over the same store — `identity:soul` is minted once,
  > never re-minted over the existing soul; a rendered block over the 8192
  > cap is truncated at the cap.
- **AC7** `kyber agent list` folds each registry store's head and prints
  name + model + provider + soul head (one line each, exit 0); empty registry
  prints nothing, exit 0. `kyber agent show <name>` prints the full fold.
- **AC8** `kyber agent set <name> <field> <value>` / `unset <field>` /
  `set-soul <name> <text>` append operator-attested `AgentSet` deltas (only
  changed fields; the fold updates; `show` reflects it). Dedup is
  semantics-aware (premortem fold): re-asserting the CURRENT fold value is a
  no-op (dedup_check absorbs it — T16); re-asserting a PREVIOUS value
  produces a NEW delta that re-wins the merge (`set A → set B → set A`
  resolves to A).
- **AC9** `kyber ctl --log <path> set-config {...}` (channel, daemon up)
  appends the same operator-attested deltas over the served interface; a
  `self_config: true` agent's `self_config.set` tool appends agent-attested
  ones. Both are door-admissible and fold per AC5.
- **AC10 (hot-swap)** A live daemon, subscribed via the T16 feed, receives an
  `AgentSet` delta; the next inference cycle runs with the rederived
  config (model/provider/prompt/soul/seed policy) — no reboot. Verified by a
  test that boots a `:reactor` daemon, appends a config delta mid-session,
  and observes the changed provider on the following engine call.
- **AC11 (retraction)** A retraction delta negates its target: the fold steps
  back to the previous live head and `show` reflects it. The store still
  contains the retracted delta (nothing is deleted).
  > verify: append a delta, append its retraction — `show` steps back to the
  > previous head; the retracted delta remains byte-present in the store
  > file (store only learns).
- **AC12 (safety harness)** A config-class failure on the first inference
  after a self-config delta auto-appends retractions (per-FIELD: exactly
  the deltas that last set the changed resolved fields; bounded, at most N
  field-steps), emits a `ConfigRollback` claim, and surfaces it in
  `ctl tail`/`status`. The classifier is explicit: 400/401/404/missing-env/
  bind/decrypt are config-class; 429/5xx/timeout are TRANSIENT (retry with
  backoff, never retract; N consecutive config-class failures required
  before any step-back — a provider brownout destroys no good deltas).
  `base_url` is operator-attested ALWAYS: an agent self-config delta may
  not change it (proxy-exfiltration P0). An operator-attested bad delta
  triggers DETECTION + NOTIFICATION only (no silent operator undo). The
  whole loop is operator-seed-gated and testable with a stubbed engine
  that fails on the changed provider; a transient-failure test proves a
  429 never rolls back.
  > verify: stubbed-engine tests — per-field retraction targets exactly the
  > deltas that last set the changed fields; a 429/timeout never retracts
  > (N consecutive config-class failures required before any step-back);
  > an agent self-config delta attempting `base_url` is refused at the
  > tool boundary.
- **AC13** `agent retract <delta-id>` (operator) negates the target delta —
  the manual undo for D5's operator path.
- **AC14 (genesis layer)** `kyber agent new <name>` appends the genesis
  default `AgentSet` delta (deepseek-v4-flash fallback layer, AC-defaults)
  FIRST, then the operator's seed delta. The fold's live head merges both —
  fields the operator named come from the seed delta, everything else from
  the genesis layer. `show` reflects the merged fold; boot uses deepseek when
  the operator named no provider flags.
  > verify: after `agent new wisp --soul "..."` with no provider flags,
  `show wisp` carries the deepseek provider (from the genesis delta).
- **AC15 (fallback is already there)** Override the provider (operator
  `agent set wisp --model <other>` or a self-config delta), then negate the
  override (`agent retract <override-id>` or the AC12 harness step-back): the
  fold returns to the genesis layer — the deepseek fallback — with no further
  deltas needed. `show` and the next boot reflect deepseek again.
- **AC16 (unset a default)** `agent retract <genesis-delta-id>` negates the
  default layer itself; the fold then has no live head for the name and boot
  falls through to the engine's hardcoded defaults (deepseek-v4-flash) —
  identical behavior to an agent with no `AgentSet` stream. The retracted
  genesis delta stays in the log (store only learns).
- **AC17 (door rejects plaintext secrets)** An `AgentSet` delta (via `agent new`/
  `set`, channel `set-config`, self-config tool, or `--from` import) whose
  secret field is neither a valid env NAME (`{"env": ...}` matching
  `^[A-Z_][A-Z0-9_]*$`) nor well-formed ciphertext (`{"enc": ...}`) is
  refused with a legible repair message. A soul/system_prompt containing an
  obvious secret shape (`sk-`, `api_`, ≥32-char base64/hex run, `KEY=` pair
  with a long right side) is refused the same way. The store never contains
  a plaintext key value.
  > verify: an attempted `agent set wisp --api-key sk-...` exits with
  > the repair message and appends NO delta; the store's `AgentSet` stream
  > contains only env names and ciphertext.
- **AC18 (legible missing-key error)** Boot with a fold whose `api_key`
  is `{"env": NAME}` and the named env var is unset/empty fails with the
  clean message (agent name, provider, the env var name, exact repair
  instruction) — never a traceback, never the key. The failure is a
  config-class failure for AC12's harness when it follows an override
  delta.
  > verify: `daemon --agent <name>` with the key env unset prints the
  > repair message and exits non-zero; no key-shaped text in the output.
- **AC19 (secrets never ride the prompt)** A `:reactor` daemon with a real
  env var set assembles a prompt: the assembled context contains no
  key-shaped string. `status`/`show`/`list` print env NAMES or ciphertext
  only. The daemon log path redacts configured key values; error messages
  never echo a key.
  > verify: prompt-assembly test asserts no `sk-`/long-hex/`KEY=` in the
  > assembled context with the key set; `show` output grep for the key value
  > is empty.
- **AC20 (encrypted-at-rest round-trip)** `agent set wisp --api-key` with
  the value read from STDIN (never argv) writes `{"enc": ...}` ciphertext
  into the store; the store, `show`, `status`, and `list` contain no
  plaintext. A `:reactor` daemon booted with that fold decrypts at the
  usage point (derived from the operator seed) and answers a live turn on
  the configured provider. A store copied WITHOUT the operator seed yields
  nothing usable (decryption fails loudly, never falls back to a wrong key).
  `agent rekey` (premortem fold) decrypts under the old seed, re-encrypts
  under the new, and appends superseding deltas — seed rotation never
  bricks ciphertext. The D2 clone-by-replay workflow states its seed story:
  a clone receives the seed out-of-band or re-provisions `{enc}` values on
  the destination (never silently scp's the root secret).
  > verify: round-trip test greps the store/`show` for the plaintext
  > (empty), then boots and observes the provider call succeed; a
  > wrong-seed boot fails with the legible decrypt error; `agent rekey`
  > makes the store decryptable under the new seed only.
- **AC21 (root secret never serialized)** The operator seed is never a
  delta value — `operator_seed_env` is env-name-only, enforced at the door
  like AC17; no `agent set` verb accepts a seed VALUE (only an env NAME).
  > verify: an attempt to write the seed value into a delta is refused;
  > the store's stream contains no 64-hex seed-shaped string.
- **AC22 (inference-boundary redaction)** A `:reactor` daemon whose
  assembled context contains a known secret VALUE (injected via a tool
  output / memory note — simulating the leak that layers 1-2 missed) sends
  NO occurrence of that value to the provider: the wire payload carries
  `[REDACTED]` in its place. A conservative shape-scan redacts an
  *unknown* `sk-`-shaped string too. Legitimate content (64-hex IDs,
  `ed25519:` authors) rides the prompt untouched (no false positives).
  > verify: with the API key value embedded in a memory note, the
  > stubbed engine's captured request body contains `[REDACTED]` and
  > never the key; a 64-hex content id in the same context is intact.
- **AC23 (overrides survive hot-swaps)** A daemon booted with a CLI
  override (`--model kimi-k3`) receives a hot-swap `AgentSet` delta touching
  an unrelated field: the override is re-applied after the re-fold, the live
  engine still runs kimi-k3, and `status` shows fold-value AND live-value
  distinctly. `show` (fold) and `status` (live) can never silently
  disagree (premortem fold).
  > verify: boot with override, hot-swap soul, assert the engine's model
  > is still kimi-k3 and `status` exposes both values.
- **AC24 (tombstone runbook)** The spec ships the miss-handling procedure:
  an operator can retract a delta that carried a plaintext secret and
  append a `SecretTombstone` claim (delta id, field, time, rotated-key
  pointer); the runbook is documented in the CLI help/README, not
  discovered after an incident. Free-text fields get the fail-closed
  entropy scan in addition to the shape-scan (premortem fold).
  > verify: the entropy scan refuses a high-entropy soul; the tombstone
  > verb appends the claim and `show`/`list` surface it.

## Out of scope
- Multi-provider routing/fallback inside one agent.
- In-process siblings / multi-daemon per BEAM (siblings = separate stores +
  federation, by design).
- Property-scoped self-config allowlists (D4 verdict: boolean for v1,
  revisit later).
- Config editing via the reified file (there is no reified file).
