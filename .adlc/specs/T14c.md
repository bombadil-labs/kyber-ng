## The slice

Three carries close here:
- **Prompt-answer-as-delta** (prompt-policy determinism hole, T12 #2): the prompt the
  model sees is answered as a STORE DELTA (deterministic, content-derived, mergeable) —
  not as an ephemeral model echo. The policy layer's prompting becomes re-derivable from
  store state like everything else.
- **Memory-read permission seam** (T13): the agent's memory reads (MemoryRead tool /
  MemoryEdited events) route through the permission seam — the same closed
  decide→refusal loop the reactor hosts — instead of being ambiently permitted.
- **Operator-key boot wiring** (attestation keys / A-B seam contract, T11c): the
  operator's key attests the agent's boot — boot wiring that makes the operator an
  explicit, store-visible participant (the A-B seam contract honored in code, not just
  on paper).

In scope: the prompt-delta claim shape + the prompt-assembly path, the memory-read gate +
its refusal routing, the operator-key boot attestation + its store presence. Out of scope:
boundary enumeration + precision bounding (T14d), the M5 engine verdict fix (the
engine-decides slice — the T14b live config discipline still applies), URL policy
extensions.

## Acceptance criteria (draft — the rumble pins the exact shapes)

- AC1 (prompt-as-delta): a prompt delta in the store re-derives the exact prompt the
  model saw — two boots over the same store produce byte-identical prompt answers (no
  wall-clock, no ephemeral echo); the prompt is a first-class, mergeable store artifact.
- AC2 (memory-read gate): a memory read routes through the gate — an allowed read
  returns the memory + records a permission GateDecision; a refused read returns a
  refusal routed through "decides", and NO memory content leaves the store (asserted,
  not assumed).
- AC3 (operator boot attestation): a boot under an operator key records a store-visible
  attestation (operator, agent, boot claims); the attestation is content-derived and
  verifiable from store state alone.
- AC4 (live, @tag :operational): a real model turn exercises the seam — prompt answered
  as a store delta (machine-checked: the assembled prompt equals the stored prompt
  delta's content), a memory read permitted/refused per the gate, operator attestation
  present in the store. (The M5-avoidance discipline applies: the tool-bearing live
  config tolerates the fabricated-refusal behavior, never asserts on it.)
- AC5 (determinism): prompt assembly, memory-gate decisions, and attestation all derive
  from store state; no wall-clock in decisions.

### D1 — Prompt-delta claim shape: KEEP P1 (per R1/R2/R3, unanimous; settled by A1/A3's substrate kill of the Jason encoder)

New wire type `"PromptAssembled"`; constructor `Events.prompt_assembled(seed, ts,
request_id, session_id, content)`. EXACTLY three pointers, `sessionId` FIRST (the
ConversationSummary precedent — the kind marker rides the first pointer role, and kind
"sessionId" routes to no subscription and matches no lens):
- `%{role: "sessionId", target: {:entity, session_id, "prompts"}}`
- `%{role: "requestRef", target: {:delta, request_id, "prompted"}}`
- `%{role: "content", target: {:string, canonical_json}}`

Order is load-bearing — the two `requestRef` readers key on the FIRST role:
`Engine.answered?/2` (engine.ex:481-486) matches ANY delta whose first role is
"requestRef" targeting the request (requestRef-first would mark the request answered
before the model call, welding the transient-error retry window shut), and
`ContextBuilder.conversation/2`'s "requestRef" clause (context_builder.ex:63-68) reads
such a delta as an ASSISTANT turn — it has a `content` pointer — poisoning AC1's
independent re-derivation with a phantom message. AC4's per-request check is a role
scan, order-independent.

`canonical_json` = **stdlib `JSON.encode!`** (the repo encoder, llm_handler.ex:161 —
Jason is not a dependency; P2's pin was factually dead) of the bare **string-keyed**
message list `[%{"role" => r, "content" => c}]` — exactly what `LlmHandler.chat/3`
receives. `ts` = the triggering `InferenceRequested` delta's `claims.timestamp`, never
wall-clock. ONE claim per assembled prompt; per-message claims rejected (all three
proposals agreed). P3's epoch/per-memory echo-pointers rejected: they widen the
id-input with derivable data and drop the requestRef that makes AC4's per-request
machine check queryable (A2/A3).

### D4 — Memory scope + the gather: KEEP P1's payload + SYNTH RULING on the second surface (payload per R1/R2/R3; the gather was R2's UNARGUED — resolved here, no hedge)

Payload: "the memory" = the resolved canon — `Memory.canon/3`'s `.content` binary.
Tool id `"memory.read"`, args `%{"entity" => entity_id}`; allowed read ⇒ ToolResult
content = canon content; unknown entity ⇒ content `""`, status `"unknown_entity"` — a
resolution outcome, never a refusal; gate strictly BEFORE resolution, so refused

executor resolves `"memory.read"` in a **dedicated run clause over the handler's
`:store` thunk** — the 1-arity closure's status is hardwired `"ok"` and the
action-data MFA cannot see the captured store, so `canon nil ⇒ {"", "unknown_entity"}`
lives in that clause (tool_executor.ex:229-249). Registry: `ToolExecutor.memory_tools
(store_fn)` exists ONLY to list the tool for `tool_specs`/`tool_key_map`; the gate
fires on tool_id membership regardless of registry origin. P2's full-record return rejected (over-discloses
provenance/chain, A1/A3); P3's bare-string adds nothing over P1 and left
unknown-entity unpinned.

**RULING — the MemoryEdited-driven context gather IS a second gated surface, gated by
a call-less mechanism** (adopting P2's catch — the only proposal that saw the surface
— on a new mechanism, since P2's own wire pin is substrate-dead: `gate_decision/7`
requires a `call_id` a gather lacks, R2-verified; and `build_messages`' ungated
`memory_notes` is a real ambient content flow the T13 carry text names). **SYNTH-NEW
mechanism, pinned exactly**:

- `Prompt.assemble/4` filters `memory_ids` through the memory epoch before building
  `memory_notes`: entity allowed ⇒ note included; entity not allowed ⇒
  **omit-from-prompt, NO GateDecision minted** (no call_id exists; omission is the
  call-less refusal grammar); epoch **forked ⇒ omit ALL memory notes** (fail-closed on
  fork); epoch **absent (ungoverned) ⇒ include all — the legacy gather behavior is
  preserved**.
- **id→entity resolution is by CHAIN MEMBERSHIP, never the delta's direct entity
  pointer**: the gather iterates memory DELTA ids while the retriever answers canon
  HEAD ids, and a canon head that is a `MemoryEdited` carries no entity pointer — the
  filter resolves each id via `Memory.resolve_set/2` to the entity whose chain
  contains it (membership transitive over the edit chain). Under `{:ok, epoch}` an id
  in NO resolvable chain is **omitted** (unprovable ⇒ fail-closed, consistent with the
  fork ruling); under `:none` it is **included** (legacy).
- The ungoverned asymmetry vs the tool's fail-closed default is deliberate and pinned:
  the gather PREDATES governance (T11b memory notes), exactly as http tools did — so
  it carries the same recorded-hole shape with the same deferred governance-default
  owner, while the tool, born in this slice, is fail-closed (A3's born-in-this-slice
  criterion applied consistently on both sides).
- Determinism preserved: the filter is a pure function of store state, so AC1
  byte-identity and the replay pre-check are unaffected (the stored claim still wins
  on replay even if the epoch changed after emission).
- Consequence for AC2's leak assertion: the sentinel scan extends to `PromptAssembled`
  content — a refused entity's content must not appear in any stored prompt, where
  "refused" means refused UNDER a governing epoch (excluded/forked); the ungoverned
  gather is the recorded legacy hole (content may appear) and is asserted separately
  as such.

The premortem must attack this ruling directly (the asymmetry, the no-GateDecision
omission, the forked-omit-all), not re-open it as a hedge.
