## The slice

Three carries close here:
- **Prompt-answer-as-delta** (prompt-policy determinism hole, T12 #2): the prompt the
  model sees is answered as a STORE DELTA (deterministic, content-derived, mergeable) —
  not as an ephemeral model echo. The policy layer's prompting becomes re-derivable from
  store state like everything else.
- **Memory-read permission seam** (T13): the agent's memory reads (MemoryRead tool /
  MemoryEdited events) route through the permission seam — the same closed
  decide→refusal loop the reactor hosts — instead of being ambiently permitted.
- **Operator-key boot wiring** (attestation keys / A-B seam contract, T11c): the
  operator's key attests the agent's boot — boot wiring that makes the operator an
  explicit, store-visible participant (the A-B seam contract honored in code, not just
  on paper).

In scope: the prompt-delta claim shape + the prompt-assembly path, the memory-read gate +
its refusal routing, the operator-key boot attestation + its store presence. Out of scope:
boundary enumeration + precision bounding (T14d), the M5 engine verdict fix (the
engine-decides slice — the T14b live config discipline still applies), URL policy
extensions.

## Acceptance criteria (draft — the rumble pins the exact shapes)

- AC1 (prompt-as-delta): a prompt delta in the store re-derives the exact prompt the
  model saw — two boots over the same store produce byte-identical prompt answers (no
  wall-clock, no ephemeral echo); the prompt is a first-class, mergeable store artifact.
- AC2 (memory-read gate): a memory read routes through the gate — an allowed read
  returns the memory + records a permission GateDecision; a refused read returns a
  refusal routed through "decides", and NO memory content leaves the store (asserted,
  not assumed).
- AC3 (operator boot attestation): a boot under an operator key records a store-visible
  attestation (operator, agent, boot claims); the attestation is content-derived and
  verifiable from store state alone.
- AC4 (live, @tag :operational): a real model turn exercises the seam — prompt answered
  as a store delta (machine-checked: the assembled prompt equals the stored prompt
  delta's content), a memory read permitted/refused per the gate, operator attestation
  present in the store. (The M5-avoidance discipline applies: the tool-bearing live
  config tolerates the fabricated-refusal behavior, never asserts on it.)
- AC5 (determinism): prompt assembly, memory-gate decisions, and attestation all derive
  from store state; no wall-clock in decisions.

## Open decisions the rumble must pin

1. Prompt-delta claim shape: kind/pointers/content (what a prompt delta IS — a "prompt"
  claim whose content is the assembled prompt? per-message claims? the exact roles).
2. Prompt-assembly path: where the prompt is assembled from store state (the reactor?
  the executor? a projector?), how "the prompt the model saw" is guaranteed identical
  (the AC1 byte-identity), and the replay semantics.
3. Memory-read gate placement: the same decide loop as the URL gate, or a distinct
  surface? The gate's inputs (what makes a memory read allowed/refused) and the refusal
  shape (wire strings riding the canonical carries).
4. Memory scope: what "the memory" IS (the store's memories? a memory index? the
  MemoryEdited history?) and what a read returns.
5. Operator attestation shape: the boot claim's kind/pointers/content, what "boot" means
  (daemon boot? agent start?), the operator key's role (attests, authorizes?), and how
  attestation interacts with the existing keyring/seed machinery.
6. Reactor/gate integration: where the new gates sit in the executor's decide chain vs
  the URL gate (order, layering, the closed loop — host, never rebuild).
7. The deterministic tests: exact seeding + per-AC anti-placebo shapes (how each test
  FAILS when the feature is absent) + the AC4 live shape.
8. Deliverables: module/test file names (deliverable-existence gate).
