# T14g — Agent Identity: Soul Docs, Profiles, and the Always-On Block

Status: OPEN (light ceremony — rumble for the design cells, one deterministic
build). Parent: T14f (in build; provisional/t14). Rails: carried.

## The framing

Hermes injects USER.md (who the user is) + MEMORY.md (agent notes) into every
turn; OpenClaw ships a person.md as the persona. Both treat identity as STATIC
blobs. kyber's unique affordance: identity is a DERIVED ENTITY — a view over
its delta stream, exactly like skills (T14f's binding framing). A "soul doc"
is not a file; it is the fold of identity primitives, rendered into the
always-on system block. And PROFILES are policy-shaped: the epoch machinery +
the gate allowlist already know how to bound visibility and capability — a
profile is a named binding of (identity view, memory/skill visibility,
capability subset), not a new storage mechanism.

## The primitives (the rumble pins the set)

Identity primitives = named entities whose canon folds into the always-on
block. Candidates:
- `soul` — who the agent IS (persona, voice, values, the "Veles" layer for
  Liet). Operator-attested (the agent does not write its own soul).
- `user` — who the operator/user is (preferences, context, how to be useful).
- `operator` — system/operator constraints (hard rules, escalation paths).
- `profile` — the active profile's own rules (per-channel behavior).

Each primitive = an entity (like `memory:cap`) with a versioned body; the
fold renders it. Writability is gated (the T14c fail-closed pattern: the
soul/user docs are operator-attested writes; agent-writable memory stays in
the memory seam).

## The always-on block (G3)

The system block in Prompt.assemble: [soul, user, operator, profile rules,
memory_notes, skill_notes, summary_notes, turns] — identity primitives FIRST,
before the ad-hoc notes. Capped (byte bound), deterministic
({timestamp, id} fold), rendered by the same lens machinery as skills.

## Profiles (G4-G7)

A profile = a named binding of THREE things:
1. **Identity view** — which primitives ride (a Discord server profile might
   ride the soul but NOT the broader user doc).
2. **Memory/skill visibility** — bounded by a policy epoch (the memory +
   skill epochs' allowlists define what the profile can see; a channel profile
   has its own epoch — no access to broader memory).
3. **Capability subset** — the gate allowlist (Gate.new(allow: [...])) ∩ the
   boot tool registry; a channel profile runs a subset of tools.

Profiles are declared (a profile-entity delta family) + selected at boot
(the reactor/attach boot takes a profile id). The SAME Kyber instance hosts
default / coding-agent / per-channel profiles — the identity view, the
epochs, and the gate differ; the store is shared but the visibility is
epoch-bounded (the atom: the store only learns; profiles bound the VIEW).

## Open design cells

G1 — the primitive set (which of soul/user/operator/profile + what else).
G2 — the delta shape: identity primitives as memory-entity family vs a
distinct identity kind (genesis impact! the T14f H5 lesson — unknown types
admit :raw).
G3 — the always-on block: exact order, byte cap, the rendering (markdown?
plain?), the fold determinism.
G4 — profile declaration: the delta family + schema (profile id, bound
primitives, epoch refs, capability list).
G5 — profile selection: boot-time opt (reactor/attach) — how the profile
id threads into the boot (the D9 lesson: which surface? attach vs reactor).
G6 — capability binding: gate allowlist ∩ registry — the exact merge; does
the profile override or intersect the boot's tools?
G7 — writability: who can write each primitive (operator-attested soul/user;
agent-writable profile-scoped notes?); the fail-closed gate mapping.
G8 — the profile-epoch wiring: does a profile REFERENCE existing epochs or
carry its own allowlist? (the skill_policy precedent: allow_entity reuse vs
new role — genesis impact again).

## Acceptance criteria (shape)

AC1 — the always-on block: a boot with a soul + user doc renders them FIRST
in the assembled prompt, deterministic, capped (the identity fold witnessed).
AC2 — profiles: a default profile and a channel profile boot on the SAME
instance; the channel profile's memory/skill visibility is epoch-bounded
(cross-profile leakage witnessed ABSENT); its capability subset is enforced
(the gate refuses what the profile doesn't allow).
AC3 — writability: the soul doc rejects agent writes (operator-attested
only); the user doc likewise; the memory seam is unchanged.
AC4 — determinism: identity + profile folds are {timestamp, id}-ordered,
replica-identical (the T14f D2 norm).

## Deliverables (shape)
