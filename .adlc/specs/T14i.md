# T14i — I/O Channels: TUI + Discord Gateway

Status: OPEN — Revision 1 (premortem fold; delta-logged at the foot) —
the converged plan below, amended by the H1–H9 pins, the M1–M14 pins, and
the L1–L8 constraints. Parent: T14h (spec committed; provisional/t14).
Rails: carried. The design cells: light ceremony for the channel-adapter;
the TUI is a direct build (mostly mechanical).

## The framing

The user's brief: "a basic TUI to start, as well as the ability to wire the
agent into a discord server if we don't already have this."

Today the agent has ONE I/O path: the reactor's prompt channel (messages
ingested as deltas, responses emitted as `message.sent` deltas, the sink
delivers via the prompt's channel pointer). There is NO terminal UI and NO
external network channel. T14i adds two surfaces over the SAME seam:

- **The TUI**: a terminal client that connects to a running daemon — the
  operator sees the agent's stream (prompts, responses, refusals, tool
  calls) and can drive it (send a message, tick, inspect state). Read-mostly
  with a send surface; the reactor remains the authority (the TUI is a
  CLIENT, never a second engine).
- **The Discord gateway**: a channel adapter — a process that connects to a
  Discord server (gateway websocket), ingests messages as `message_received`
  deltas (the channel pointer = the Discord channel id), and delivers
  `message.sent` deltas back as Discord messages. The agent's identity
  (profile, soul) is bound per-server (T14g's channel profiles: a per-server
  profile with a capability subset and no broader-memory access).

## The channel-adapter seam (the design core)

The reactor already has the pattern: messages in as deltas, responses out as
deltas, the channel pointer routing delivery. The channel adapter is a NEW
transport on that seam:

- ingest: `message_received` deltas minted from the transport's events
  (Discord message → delta; TUI keystroke → delta) — the same event family
  the reactor already dispatches (the T14c determinism test mints these).
- deliver: `message.sent` deltas read from the store (or a subscribe seam)
  routed by the channel pointer (Discord channel id / TUI stdout).
- the adapter is a process (a GenServer), NOT a second engine — the reactor
  stays the single authority; the adapter is transport plumbing.

## Discord specifics (the design cells)

- D1 — the gateway: a raw websocket (nostrum/erlef? a minimal WS client?)
  vs a library. Rails: deps/ is frozen — a new dependency is a RAILS
  VIOLATION unless carried as an explicit exception. The cell: do we use an
  existing dep (hackney is present — ws support?) or hand-roll the minimal
  gateway (websocket handshake + gateway events + heartbeats)? Hand-rolled
  is house-consistent (the harness is dependency-minimal).
- D2 — token handling: the DISCORD_BOT_TOKEN via the blocked-script env
  loader (KYBER_OPERATIONAL=1 pattern) — NEVER in the store, never in a
  delta, never in the repo. The token is a transport credential, not a
  store artifact.
- D3 — per-server profiles: the gateway binds a profile per Discord server
  (T14g): the server's channel id → a profile id → its epoch/gate/identity.
- D4 — message mapping: Discord message → message_received delta (channel
  pointer = the server+channel id; author = the human operator's attestation
  key for the server? — the operator-attestation seam (T14c) maps to
  Discord users how? — the cell: who signs a Discord message's received
  delta; the operator seed per server).
- D5 — delivery: message.sent → Discord message (content + the reply/thread
  context); rate limits (Discord's 5/5s channel limit — a throttle seam).
- D6 — the TUI surface: read the daemon's stream (a tail/inspect mode) +
  send; the TUI binds to the daemon how (a socket? stdin/stdout of a
  `kyber tui` command? the daemon's existing socket protocol?).

## The TUI specifics (mostly mechanical)

- `kyber tui` — connects to a running daemon (the socket), prints the
  stream (prompts/responses/refusals with the profile tag), accepts input
  (send a message as the operator), and exposes inspect commands (state,
  store count, active profile). No-sleep, deterministic-friendly; the TUI is
  a thin client — no engine logic.

## Acceptance criteria (shape)

AC1 — the TUI: connects to a running daemon, streams the agent's activity,
sends an operator message (the message becomes a message_received delta and
the agent responds).
AC2 — the Discord gateway: connects to a server, ingests a message as a
delta, delivers the response (the loop witnessed with a fake transport —
never a real token in tests; the live gate uses the blocked-script env
loader + KYBER_OPERATIONAL=1).
AC3 — profile binding: a per-server profile is selected by the channel
pointer (the T14g machinery); capability subset + memory bounds enforced.
AC4 — no engine split: the reactor stays the single authority (a TUI/DC
message and a reactor-tick message produce identical behavior).
AC5 — the token never appears in the store, deltas, or repo (the credential
hygiene witness).

## Design resolution (converged plan)

The rumble (P1/P2/P3 → A1/A2/A3 → R1/R2/R3, `.adlc/rumble-t14i/`) converged
on every contested cell, including the one coin-flip (intents — settled
explicitly below). The binding framing held: **the log is the stream, the
socket is the door, the adapter is plumbing** — the reactor stays the single
authority; this slice builds exactly two genuinely new pieces (the
daemon-owned channel socket and the transport behaviour + pure codec) and
threads the T14g profile machinery onto the reactor path (the recorded G5
carry comes due here). The resolutions below are pins, not sketches. Two
spec premises died in the rumble and are recorded: **"hackney is present"
is false** (mix.exs — rhizomatic is the ONLY dep; there is no ws-capable
arm to pick), and **"the daemon's existing socket protocol" does not
exist** (the only socket in the repo is the federation Peer; the seam is
BUILT this slice, with Peer as the construction precedent).

### D1 — the transport seam: a behaviour + a pure codec, hand-rolled (moderate — the codec)

- **The behaviour, 3 pinned callbacks + owner-message frames**:
  `Kyber.Agent.Channel.Transport` — `connect(opts, owner_pid)`,
  `send_frame(conn, iodata)`, `close(conn)`; inbound frames arrive as
  `{transport_ref, {:frame, opcode, payload}}` messages to the owner
  (active-once plumbing lives inside the impl). The frame is PINNED — an
  unpinned seam can't ride a diff metric (the argue round's recorded
  warning); injection is `{module, state}` at adapter construction (the
  http_client.ex behaviour precedent — a fake in tests, the real impl at
  the live edge, never a compile-time swap).
- **A SECOND `{module, state}` injection: the DELIVERY seam (H4)** —
  Discord message-create is REST-only (`POST /channels/{id}/messages`
  with `Authorization: Bot <token>`); the gateway WS carries
  heartbeats/identify/resume/presence — never channel messages. The
  delivery impl is REST-shaped (the http_client.ex:1-9 precedent —
  `post(url, headers, body, state)`): the fake RECORDS url/headers/body;
  the token rides ONLY that seam's Authorization header, never the frame
  stream; the "fake's sends EQUAL the store's ResponseDelta content"
  witness SCOPES to the delivery seam — the frame-stream fake is NOT held
  to that equality (heartbeats/pongs break it, M3).
- **The pure codec, mask-INJECTED**: `encode_frame(payload, opcode,
  mask_key)` / `decode_frames(buffer) :: {frames, rest}` — RFC 6455 client
  side; the 4-byte mask key is an ARGUMENT (crypto-random only at the live
  edge, deterministic in tests) and is never trusted from the peer.
  Client frames masked, server frames unmasked, extended lengths 126/127,
  fragmentation reassembly, close(0x8). **Strictness pinned (M3)**: the
  decoder REJECTS (returns an error — never raises) masked server frames,
  RSV bits set, control frames >125, and fragmented control frames — a
  raising decoder kills the adapter owner on garbage bytes. ping(0x9)→
  pong(0xA) cannot live in the pure codec (it can't send): the transport
  IMPL auto-pongs internally (pinned), so the frame-stream fake observes
  pongs — exactly why the H4 equality witness scopes to the delivery seam.
- **Heartbeat-ack-resume (P3's pin)**: heartbeat via `Process.send_after`
  at the hello interval (the daemon ticker doctrine — never
  `Process.sleep`); a missed heartbeat-ack ⇒ close + op-6 resume with the
  stored `(session_id, seq)`; op-9 non-resumable ⇒ re-identify.
  **Reconnect cadence pinned (M2)**: a min backoff + jitter via
  `send_after` (a tight resume/identify loop against a dead gateway burns
  Discord's ~1000-identifies/day budget), and the RESUME gateway URL is
  CACHED — it differs from the identify URL.
- **Dep arm: hand-rolled, ZERO new deps.** A new dependency is a RAILS
  VIOLATION unless the carry above (T14i.md "Carries", the websocket
  clause) is exercised explicitly in the slice record. The behaviour
  boundary + pure codec are the deliverable either way — they are what
  makes the carry honest.
- **M13 — the live TLS arm needs the recorded code-path repair**: under
  `mix run` (prune_code_paths) `:code.which(:ssl)` is `:non_existing` and
  `ensure_all_started(:ssl)` fails "no such file or directory" (probed);
  the repo already records this exact incident + repair
  (`ensure_http_apps/0` + `otp_ebin_on_path/1`, http_client.ex:64-91,
  private today). Extract/share that repair for the gateway's `:ssl` arm
  or the live connect fails the same recorded way.

### Intents — the coin-flip, SETTLED: 33280

**`33280`** = GUILD_MESSAGES (1<<<9) | MESSAGE_CONTENT (1<<<15)
(arithmetic verified: 512 + 32768; L3). No proposal consumes GUILD_CREATE
— the per-server binding rides explicit boot config plus the dispatch
payload's own `guild_id`, so GUILDS is dead weight (P1 conceded in its
own argue; R1/R2 switched to P3's pin). MESSAGE_CONTENT stays privileged
either way — the operator enables it in the portal (the ops note recorded
in the adapter moduledoc). **L3 — DM channels are structurally
unreachable under this mask** (no 1<<<12): guild-only is consistent with
one-server-per-instance; note for the ops doc.

### D2 — token hygiene: env-at-boot, argv exits 2, proven-live scanner (easy)

- `DISCORD_BOT_TOKEN` is read from the environment at gateway boot ONLY —
  the CLI takes env NAMES, never values; **`--token <value>` on argv is a
  usage error, EXIT 2** (ps-visible). Absent env ⇒ fail-closed error at
  boot — no default, no retry, no file fallback.
- **The AC5 witness is the proven-live sentinel scanner**: run the full
  fake-transport loop with a sentinel token; first mint a claim carrying
  the sentinel and assert the scanner FINDS it (a dead scanner can't claim
  absence), THEN assert the real token is absent from the store bytes, the
  on-disk log bytes, and the rendered status. **Never a lib/ grep** — the
  scan is over store/log/status bytes, not the repo tree.
- **M12 — the token is held OUTSIDE inspectable state** (a closure/holder,
  not adapter state fields) or `format_status/1`-redacted: a crash report
  prints process state to the logger, invisible to the byte scanner. The
  USER-CONTENT false-positive class is RECORDED: a user pasting the token
  into Discord legitimately lands it in `MessageReceived` content — the
  deterministic suite never sees that shape, but any productionized reuse
  must be content-aware. The liveness-minted sentinel persists in the
  test store's log bytes — per-test stores only.
- The live gate inherits the operational shape verbatim: `@moduletag
  :operational` + `KYBER_OPERATIONAL=1` + `DISCORD_BOT_TOKEN` set;
  the deterministic suite never sees a token (the fake takes a sentinel).

### D3 — profile scope: ONE profile per boot; the threading is the keystone (moderate — the threading)

- **ONE profile per daemon boot.** The threading = daemon `:profile` opt →
  `daemon.reactor_opts` (daemon.ex:534-542 — the whitelist that drops it
  today) → `Reactor.start_link` opt → the hosted engine's `engine_opts`
  `:boot` (reactor.ex:443-451 carries no `:boot` key at all) — **three
  touchpoints, all deliverables**. This lifts T14g G5's recorded carry.
  **H8 — the capability intersect is the FOURTH touchpoint**: the
  profile-excluded tools ride the TOOLS list, not the boot tuple —
  daemon.ex:534-542 threads `:engine` untouched → reactor.ex:441's tools
  default (`Keyword.get(opts, :tools, ToolExecutor.stub_tools())`) →
  `tool_specs`/`tool_key_map` (reactor.ex:446-447). The intersect MUST be
  consumed at the engine CONSTRUCTION (reactor.ex:441) so profile-excluded
  tools are NOT executable (the existing enforcement spelling is
  tool_executor.ex:707 "unknown tool ").
- **The per-server mapping is EXPLICIT adapter state**: one server per
  gateway instance; N servers = N instances (over N stores — the log lock
  and the two-engines-double-answer constraint both forbid sharing). P3's
  per-turn `ChannelBinding` is a **recorded carry** — it violates T14h
  H6's one-profile-authority-per-assembly.
- **The intersect helper is the ONE shared helper** (T14g M1): the
  capability intersect is EXTRACTED once from the attach-private
  `profile_tools/2` (agent.ex:127-137 — the single-var `Map.take`) and
  consumed by BOTH `Agent.attach/1` AND the channel daemon's engine
  construction (reactor.ex:441, per H8) — never two intersects, never a
  private duplicate.
- **Profile MANDATORY at gateway boot — no unbound case.**
  `profile_view/3`'s profile-less arm is fail-open (prompt.ex:499-506 —
  `profile_view(_set, _author, nil), do: nil`; the nil-view `gather_ids/3`
  leg at prompt.ex:404 keeps memory bounds DARK — cite by name); an
  unbound gateway channel is exactly the AC3 leak, so the gateway refuses
  to boot without a profile (`{:error, {:unknown_profile, name}}` parity
  on a bad name).
- **H7 — profile-without-operator-seed REFUSES boot**: the enumerated
  threading can yield `{name, nil}` (profile named, seed env absent/
  unnamed), which renders profile-LESS while `replay_key/2`'s
  `{name, nil}` clause (prompt.ex:488) keeps minting keyed
  PromptAssembled claims — a silent, unbounded AC3 violation (probed). The
  channel-daemon boot consumes the SAME `boot_context/1` helper as attach
  (agent.ex:103; `{_name, nil} -> {:error, {:unknown_profile, name}}`) or
  replicates its refusal — `--profile` with an absent/unnamed
  operator-seed env refuses boot.
- **Per-server seed = a pinned pure deterministic KDF (M4)** —
  `Keys.derive_seed/2` does NOT exist (probed: `function_exported? →
  false`; keys.ex has mint/load/import/author/sign) and its byte
  construction was free (order/separator/hex-vs-raw/context string) —
  two conforming builds would derive different per-server authors. PINNED
  construction: `:crypto.hash(:sha256, master_bytes <> <<0>> <> context_bytes)`
  — raw master bytes, a 0x00 separator, UTF-8 context bytes — lowercase
  hex output; context = `"kyber:discord-server:" <> server_id`, spelled
  in the moduledoc. Portable, zero new key files; two servers derive
  distinct authors, the same server re-derives the same author across
  boots.

### D4 — mapping, attribution, spellings, and the loop guards (moderate — the mapping)

- **Discord-user attribution is a RECORDED CARRY**: the `MessageReceived`
  genesis schema is closed (genesis.ex:150-157) and the compiler refuses
  unknown roles at the door (compiler.ex:295-312) — there is no schema
  room for a user pointer this slice; per-user identity is a genesis
  evolution later, never a silent claim now.
- **Entity ids are spec-prefixed and server-qualified** under the frozen
  spec/01-events.md:17-19 namespace rule:
  `channel:discord:<server>:<channel>`,
  `message:discord:<server>:<channel>:<snowflake>`,
  `session:discord:<server>:<channel>`; the TUI rides `channel:tui` /
  `session:tui` / `message:tui:<ts_ms>:<seq>`. Bare `discord:` forms are
  rejected — the frozen spec outranks them. **L2**: the spec's examples
  show 2-id forms (`channel:discord:<id>`, `message:discord:<id>:<id>`);
  examples are NON-normative — the 3-id server-qualified resolution
  governs. **M10 — the TUI id carries a uniqueness component**: two
  identical sends in the same millisecond otherwise mint identical
  claims → identical content-derived ids → merge-is-union silently drops
  the second; pin `message:tui:<ts_ms>:<seq>` with a daemon-side
  monotonic per-ms `seq` (Discord rides unique snowflakes; the TUI has no
  such source).
- **Replay dedupe is stateless, content-derived re-mint identity**: a
  gateway reconnect replay re-mints the SAME delta id (transport-derived
  ts + snowflake-derived message id) and merge-is-union dedupes it — no
  adapter seen-set (its justifying scenario is precluded by the ts pin,
  and a seen-set dies on restart anyway).
- **The echo guard is a bot/self PRE-MINT drop**: dispatches with
  `author.bot == true` OR the bot's own id are dropped BEFORE any delta is
  minted — else the adapter's own deliveries re-ingest into an unbounded
  self-conversation (transport noise never reaches the delta layer).
- **L7 — the `by` entity differs across ingest paths** (recorded, not a
  bug): socket sends mint `human:<operator-pub>` (daemon-signed);
  `Harness.ingest` mints `human:<human-key-pub>` (harness.ex:48-51). The
  reactor is author-blind (`handle_received/2`, reactor.ex:78-84 — probed
  exactly-one chain for socket ingest), so AC4 holds; the store simply
  records both forms for the same human across paths.

### D5 — delivery: mode-independent poll, boot watermark, store-derived replies, grapheme splits (easy)

- **The delivery read = poll `DurableStore.set()` @250 ms** (`send_after`
  ticker) **+ explicit `sync/1`** as the tests' no-sleep drive —
  mode-independent by construction. A `Gather.subscribe("sent")` arm is
  REJECTED: it is structurally dead under `loop: :reactor`
  (reactor.ex:212-218/222-227; daemon.ex:163-170/290-298 — the recorded
  mode trap).
  In-poll delivery order is by `{ts, id}` (M11) — the sent ts is engine
  wall-clock ms (engine.ex:750 `now/0`), so the order is total and a poll
  drains deterministically.
- **Reboot watermark = boot-high-water-mark**: the delivery cursor starts
  at the max `{ts, id}` of matched `sent` deltas AT BOOT — history is
  NEVER re-delivered on reboot (an unpinned first-boot cursor re-delivers
  everything); within a boot a delivered-id set gives exactly-once.
  **M11 — the across-restart residual is AT-MOST-ONCE WITH SILENT LOSS,
  not at-least-once** (the carry's label is corrected): a crash between
  poll-read and delivery loses that delta permanently (it sits below the
  next boot's watermark). Duplicates across restarts are structurally
  impossible under the watermark — EXCEPT a zombie+successor adapter pair
  both polling: pin SINGLE-OWNER (one adapter per store) and
  START-AFTER-STORE (DurableStore replays in init, durable_store.ex:93-105).
  A store-visible delivery marker = genesis evolution = carry; the
  within-boot delivered-id set's unbounded growth (L4) is fine at slice
  scale and its pruning rides the same carry.
- **Reply/thread context is store-derived** (spec D5's letter): the out-id
  `"message:reply:" <> prompt_id` resolves in the store to the received
  delta, whose entity carries the original snowflake — the adapter replies
  in-thread with ZERO adapter-side mapping state.
- **The 2000-CODEPOINT cap, cut at grapheme boundaries (H3)** —
  Discord's live cap counts codepoints (probed: 2000
  graphemes of "👨‍👩‍👧‍👦" = 14,000 codepoints = 50,000 bytes → API 50035).
  Each chunk is ≤ 2000 CODEPOINTS; the cut lands ONLY at a grapheme
  boundary (never severing a grapheme), newline-first when a newline is
  within the chunk; concatenation of the chunks is byte-equal to the
  original; never truncate, never ellipsis-repair. The split is
  deterministic and its determinism is WITNESSED in the suite
  (String/`:unicode` functions probed available).

### D6 — the socket: daemon-owned UDS, JSONL, 0600 at bind (easy)

- **A daemon-owned stdlib socket, UNIX-domain**: `:gen_tcp` with
  `{:local, <log>.sock}`, **JSONL line frame (pinned)**. Filesystem
  permission is real access control where loopback TCP is any-local-user;
  the sock path rides the lock-sibling discipline (daemon.ex:585) — **the
  discovery file IS the socket**; no port file exists.
- **H1 — the frame discipline is RECV-ACCUMULATE, not one-recv-per-line**:
  on BOTH socket arms, accumulate packets until the trailing `\n` before
  parsing (safe for JSON — raw newlines never appear inside JSON strings;
  the peer.ex:276-288 blank-line precedent does NOT carry to
  terminator-less JSONL). Probed: a 1,000,001-byte line is delivered as
  685 fragments at `{:packet, :line}` (first fragment 1460 bytes;
  concatenation alone reconstructs it), and `{:line_length, n}` is
  REJECTED on local sockets (`:badarg`). The suite carries a
  **>64KB-line test** (a long status render / large delta over the wire).
- **H2 — stale-socket reclaim**: a kill -9 leaves `<log>.sock` behind and
  the next boot's bind fails `{:error, :eaddrinuse}` even with no live
  holder (probed; only `File.rm` unblocks). UNDER the held lock (the
  single-owner proof; `take_lock/1` at daemon.ex:587), `File.rm` a stale
  `<log>.sock` BEFORE bind — the daemon lock's dead-pid reclaim
  (daemon.ex:595-600) is the precedent — and remove it in `terminate/2`
  (daemon.ex:249, which today removes only the lock). Without this, a
  `restart: :transient` boot crash-loops into supervisor give-up.
- **Mode 0600: chmod IMMEDIATELY after `listen`, before the accept loop
  serves (M1)** — UDS binds 0755 by default and `:gen_tcp` has no mode
  option, so "0600 at bind" is not atomically achievable; `File.chmod(
  0o600)` right after listen (the peer.ex:169-197 shape) or bind inside a
  0700 directory; the residual pre-chmod queue window is RECORDED in the
  moduledoc. With daemon-side signing the client holds zero key material,
  so the filesystem permission IS the auth boundary — pinned, not
  incidental.
- **The verb set: `tail` / `send` / `status` / `tick`** — the framing's
  "send a message, tick, inspect state", complete. **M7 — `tail` is NOT a
  content stream**: the socket carries only NEW-LINE NOTIFICATIONS; the
  rendered content always comes from the log FILE (the pinned stream
  source) — the rejected "live-only socket tail" arm and the verb set
  cannot both be built.
- **M8 — minimal JSONL wire schemas (pinned, both directions)**: requests
  are `{"verb":"tail"}`, `{"verb":"send","content":"<text>"}`,
  `{"verb":"status"}`, `{"verb":"tick"}`; responses are `{"ok":true}`
  or `{"error":"<spelling>"}` with error spellings
  `no_operator_seed` / `unknown_profile` / `malformed`. The send payload
  is content-only (no client ts); the DAEMON stamps the received ts at
  admission — the TUI keystroke clock is display-only, never in the delta
  id. Two builds must speak one wire.

### The TUI — non-booting, keyring-less, log-tail rendered

- **`kyber tui` is a NON-booting command class**: the TUI never boots
  `:kyber` — a booting TUI is a second `DurableStore` on the live log
  (durable_store.ex:6-7, the N1 second-store trap). The preflight arm is
  pinned (cli.ex:79-97) and — with signing settled daemon-side — **SKIPS
  keyring resolution entirely** (R1's unargued, adopted): zero client key
  material.
- **H6 — the dispatch gets a THIRD preflight outcome: RECOGNIZED,
  NON-BOOTING.** `check_command(_command) -> :run` (cli.ex:126) auto-admits
  ANY new command name into the BOOTING path, and `run/1`'s tests never
  reach `main/1` (the recorded invisibility, cli.ex:62-76) — a
  `dispatch(["tui"])` arm alone passes `mix test` and still boots a second
  store in the escript. The preflight must distinguish usage | booting |
  recognized-non-booting, with `tui` in the third class. **The suite
  carries an ESCRIPT-LEVEL witness of the AC9 smoke class** (the
  cli_test.exs:445-448 pattern) asserting `kyber tui` boots NOTHING — the
  second-store trap is VM-local-registered-name-guarded only
  (durable_store.ex:47-49) and the TUI never takes the daemon lock
  (daemon.ex:155).
- **The stream source = log-file tail + a pure `render_line/1`**: the log
  is the complete record (every renderable artifact is a persisted delta),
  so the tail is late-attach-safe and the renderer is purely testable; a
  live-only socket tail shows no history and rides the mode-fragile
  dispatch path — rejected. P1's render grammar
  (`>` received / `<` sent / `!` refusal / `~` tool call / `=` result,
  content elided at 120 GRAPHEMES via grapheme-safe `String.slice/2` —
  never `binary_part`, which severs UTF-8 (M9) — non-renderable kinds →
  `nil`) rides the build. **M6 — the tail rides the HOLD discipline**: a
  torn tail line at EOF is HELD, not skipped — the daemon's precedent is
  `classify_line/4`'s `{:error, _} when at_tail? -> :halt` (daemon.ex:318-
  325); `Log.stream/1` (log.ex:53-61) has NO hold and strips EOL blindly
  (log.ex:85 `strip_eol/1`), so the TUI's cursor must not advance past a
  held line. Pin: invalid-JSON-at-tail = HOLD, distinct from
  non-renderable-kind = SKIP. **L6 — the render is not liveness-aware**
