# T14i — I/O Channels: TUI + Discord Gateway

Status: OPEN (light ceremony for the channel-adapter design; the TUI is a
direct build — the design cells are mostly mechanical). Parent: T14h (spec
committed; provisional/t14). Rails: carried.

## The framing

The user's brief: "a basic TUI to start, as well as the ability to wire the
agent into a discord server if we don't already have this."

Today the agent has ONE I/O path: the reactor's prompt channel (messages
ingested as deltas, responses emitted as `message.sent` deltas, the sink
delivers via the prompt's channel pointer). There is NO terminal UI and NO
external network channel. T14i adds two surfaces over the SAME seam:

- **The TUI**: a terminal client that connects to a running daemon — the
  operator sees the agent's stream (prompts, responses, refusals, tool
  calls) and can drive it (send a message, tick, inspect state). Read-mostly
  with a send surface; the reactor remains the authority (the TUI is a
  CLIENT, never a second engine).
- **The Discord gateway**: a channel adapter — a process that connects to a
  Discord server (gateway websocket), ingests messages as `message_received`
  deltas (the channel pointer = the Discord channel id), and delivers
  `message.sent` deltas back as Discord messages. The agent's identity
  (profile, soul) is bound per-server (T14g's channel profiles: a per-server
  profile with a capability subset and no broader-memory access).

## The channel-adapter seam (the design core)

The reactor already has the pattern: messages in as deltas, responses out as
deltas, the channel pointer routing delivery. The channel adapter is a NEW
transport on that seam:

- ingest: `message_received` deltas minted from the transport's events
  (Discord message → delta; TUI keystroke → delta) — the same event family
  the reactor already dispatches (the T14c determinism test mints these).
- deliver: `message.sent` deltas read from the store (or a subscribe seam)
  routed by the channel pointer (Discord channel id / TUI stdout).
- the adapter is a process (a GenServer), NOT a second engine — the reactor
  stays the single authority; the adapter is transport plumbing.

## Discord specifics (the design cells)

- D1 — the gateway: a raw websocket (nostrum/erlef? a minimal WS client?)
  vs a library. Rails: deps/ is frozen — a new dependency is a RAILS
  VIOLATION unless carried as an explicit exception. The cell: do we use an
  existing dep (hackney is present — ws support?) or hand-roll the minimal
  gateway (websocket handshake + gateway events + heartbeats)? Hand-rolled
  is house-consistent (the harness is dependency-minimal).
- D2 — token handling: the DISCORD_BOT_TOKEN via the blocked-script env
  loader (KYBER_OPERATIONAL=1 pattern) — NEVER in the store, never in a
  delta, never in the repo. The token is a transport credential, not a
  store artifact.
- D3 — per-server profiles: the gateway binds a profile per Discord server
  (T14g): the server's channel id → a profile id → its epoch/gate/identity.
- D4 — message mapping: Discord message → message_received delta (channel
  pointer = the server+channel id; author = the human operator's attestation
  key for the server? — the operator-attestation seam (T14c) maps to
  Discord users how? — the cell: who signs a Discord message's received
  delta; the operator seed per server).
- D5 — delivery: message.sent → Discord message (content + the reply/thread
  context); rate limits (Discord's 5/5s channel limit — a throttle seam).
- D6 — the TUI surface: read the daemon's stream (a tail/inspect mode) +
  send; the TUI binds to the daemon how (a socket? stdin/stdout of a
  `kyber tui` command? the daemon's existing socket protocol?).

## The TUI specifics (mostly mechanical)

- `kyber tui` — connects to a running daemon (the socket), prints the
  stream (prompts/responses/refusals with the profile tag), accepts input
  (send a message as the operator), and exposes inspect commands (state,
  store count, active profile). No-sleep, deterministic-friendly; the TUI is
  a thin client — no engine logic.

## Acceptance criteria (shape)

AC1 — the TUI: connects to a running daemon, streams the agent's activity,
sends an operator message (the message becomes a message_received delta and
the agent responds).
AC2 — the Discord gateway: connects to a server, ingests a message as a
delta, delivers the response (the loop witnessed with a fake transport —
never a real token in tests; the live gate uses the blocked-script env
loader + KYBER_OPERATIONAL=1).
AC3 — profile binding: a per-server profile is selected by the channel
pointer (the T14g machinery); capability subset + memory bounds enforced.
AC4 — no engine split: the reactor stays the single authority (a TUI/DC
message and a reactor-tick message produce identical behavior).
AC5 — the token never appears in the store, deltas, or repo (the credential
hygiene witness).

## Deliverables (shape)
