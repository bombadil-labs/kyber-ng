# T4 — Loop 4: The Harness Loop — gather → translate → sign → persist → view

## Context

T1–T3 built the machinery: the door (Store.admit/2), the durable store (Log +
DurableStore), the production wire (Kyber.Wire), the supervision tree (Kyber.Application).
Nothing yet RUNS the loop — "a Discord message in, a model response out" at the atom (the
founding objective, SPEC.md). T4 wires it: a source event in → a signed claim persisted →
a materialized view out. The real transport (Discord etc.) is gated on the substrate L4
reactor; T4 builds the loop against an injectable SOURCE interface (a plain map shape)
with fake sources in tests — the plugin ticket later is a thin adapter on this interface.

The claim builders (T1) pin the signing: `Events.message_received(human_seed_hex, ts,
message_id, channel_id, session_id, content)` signs with the HUMAN key; `Events.message_sent(
agent_seed_hex, ts, response_delta_id, out_message_id, channel_id, content)` signs with the
AGENT key. `Kyber.Keys` has `load_agent_seed/1`, `author_for_seed/1`, `sign/2` — and
`import_human_seed/2` writes human.seed but NOTHING loads it; T4 adds `load_human_seed/1`
(mirroring load_agent_seed/1, reading human.seed).

## Requirements

1. **Kyber.Harness** — the loop, pure + the running store (no new process; the
   app-started DurableStore is the sink). Verification: `mix test test/harness_test.exs`.

   ```elixir
   ingest(source_event, keyring_dir) -> {:ok, id} | {:error, reason}
   agent_event(model_event, keyring_dir) -> {:ok, id} | {:error, reason}
   view() -> [claims]   # materialized from DurableStore.set()
   ```

   `ingest/2`: source_event is the injectable SOURCE shape — a map
   `%{"message_id" => ..., "channel_id" => ..., "session_id" => ..., "content" => ...}`
   (optionally `"ts"` => float-ms for deterministic tests; default now as float ms, D14).
   Pipeline: load the HUMAN seed (Keys.load_human_seed/1) → Events.message_received/6 →
   Wire.envelope/1 → DurableStore.append/1 → `{:ok, envelope_id}`. Any error is a tagged
   tuple, never a crash; a refused delta returns the door's reason unchanged.
   `agent_event/2`: the response half — same pipeline with the AGENT seed and
   Events.message_sent/6 from `%{"response_delta_id" => ..., "out_message_id" => ...,
   "channel_id" => ..., "content" => ...}`.
   `view/0`: the store's delta set materialized as a list of claims (the vault-as-view
   lens is a later ticket; this is the plain claims view).
2. **Kyber.Keys.load_human_seed/1** — mirrors load_agent_seed/1 but reads `human.seed`
   (T1's import_human_seed/2 writes it; the harness must be able to load it).
   Verification: `mix test test/keys_test.exs`.
3. **Config** — `config/config.exs` gains `keyring_dir` (default `~/.kyber` — same
   HOME guard as log_path); `config/test.exs` overrides it to the tmp dir. The keyring
   dir is where human.seed + agent.seed live (Keys API already takes a home_dir; the
   harness passes the configured dir). Verification: `mix test test/harness_test.exs`.
4. TDD; no Process.sleep; `mix format` clean. Verification: `grep -r "Process.sleep"
   test/` finds nothing, `mix format --check-formatted` exits 0.

## Acceptance Criteria (each names its verification method)

- **AC1 — The suite compiles and passes; T1–T3 test files byte-untouched.**
  Verification: `mix test` exits 0 with no skips; `git diff <pre-T4-commit> -- test/`
  touches only test/harness_test.exs and test/keys_test.exs.
- **AC2 — End-to-end ingest: a fake source event ingests to a persisted, verified
  claim.** After `{:ok, id} = Harness.ingest(source_event, keyring_dir)`: the envelope is
  in `DurableStore.set()` (member by id); the id equals `Delta.id_hex(claims)` (content
  address); the claim's author equals `Keys.author_for_seed(human_seed)`; the signature
  verifies (re-admitting the envelope through the door returns `{:ok, _}` — admitted
  means verified).
  Verification: `mix test test/harness_test.exs`.
- **AC3 — Restart survival: ingest → supervised restart → the claim is still there.**
  `Application.stop(:kyber)` + `ensure_all_started` on the same log path, then
  `Harness.view()` contains the claim (replay through the door).
  Verification: `mix test test/harness_test.exs`.
- **AC4 — The response half: `agent_event` signs with the AGENT key (author = agent
  pubkey), persists, and the view shows BOTH claims (the loop's two halves, union).**
  Verification: `mix test test/harness_test.exs`.
- **AC5 — The source interface is injectable: a second fake source shape (different
  channel/content) flows through unchanged — distinct ids, both in the view; the map
  fields land in the claim's pointers exactly as translated by Events.**
  Verification: `mix test test/harness_test.exs`.
- **AC6 — Missing keyring fails cleanly: no human.seed → `{:error, :no_human_seed}` (or
  the loader's error) — a tagged tuple, never a crash; no keyring dir → a clear
  `{:error, _}`.**
  Verification: `mix test test/harness_test.exs`.
- **AC7 — Deterministic timestamps: an explicit `"ts"` in the source event lands in the
  claim's timestamp EXACTLY (float ms, D14 — no coercion).**
  Verification: `mix test test/harness_test.exs`.
- **AC8 — No Process.sleep anywhere in test/.**
  Verification: `grep -r "Process.sleep" test/` finds nothing.
